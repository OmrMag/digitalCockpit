01
Overview

System Overview

The Digital Construction Cockpit is an internal web platform deployed at ALEC Holdings. It provides a single interface for managing users, running data extractions, and processing access requests across three construction technology platforms — Revizto Morta Forma / ACC — replacing previously manual, per-platform administration.

The system is organised around two concerns: a browser-facing web layer that handles UI and all inbound API calls, and a script layer of standalone Python modules that interact with the external platforms. The two layers are decoupled through a file-based config contract and a set of environment variables injected at subprocess launch time.

All runtime state — credentials, project registry, invite logs, portal submissions, token caches — is persisted in Azure Blob Storage so the application process is stateless and can be restarted without data loss.

Registry

Project Registry

projects_registry.json in blob storage is the backbone of the entire access model. It maps a short project key to all platform identifiers, assigned admins, and live-synced metadata for that project. Every scoped operation in the system — what a user sees in the sidebar, what appears in search results, which tags and roles populate invite dropdowns — is derived from this file.

{
  "rak-central": {
    "name":    "RAK Central",
    "admins": ["oawad@alec.ae", "srajendren@alec.ae"],    // ← only these users see this project
    "platforms": {
      "revizto": {
        "project_uuid":  "1cc01307-7d5a-4e97-...",
        "region":        "dubai",
        "roles":         [{ "id": 5, "name": "BIM Coordinator" }, ...],    // synced
        "license_roles": [{ "id": 1, "name": "Guest" }, { "id": 2, "name": "Collaborator" }, { "id": 3, "name": "Content Creator" }]
      },
      "morta": {
        "hub_id": "406ed81a-...",
        "tags":   [{ "name": "ALEC-MC01-Procurement", "tag_reference_id": "..." }, ...]    // synced
      },
      "forma": {
        "project_id": "6bf6b4f6-...",
        "companies":  [{ "id": "...", "name": "VOLTAS LIMITED" }, ...],    // synced
        "roles":      [{ "id": "...", "name": "Project Admin" }, ...]          // synced
      }
    }
  }
}

Registry sync (POST /api/registry/project/{key}/sync) fetches live data from each platform and writes it back. If the syncing admin has not configured their Morta API key or Forma credentials, the system falls back to the owner's credentials — except for Morta, where keys are strictly personal and no fallback is applied.

Access Rule Only oawad@alec.ae (owner) can create, update, or delete registry entries. Write routes use require_owner. GET /api/registry returns a user-scoped subset — non-owners only receive projects where their email appears in admins[].

Config

Config System

Every admin has a personal config file in blob: config_{email}.json. The owner's config additionally holds the shared Forma/ACC credentials that all other admins inherit when their own are absent. Before running any extraction script, build_script_config() merges the admin's personal config with the owner's shared Forma block and writes the result to temp/{email}/_cockpit_config.json. Scripts never read from blob directly — they only read this temp file via the COCKPIT_CONFIG environment variable.

05
Auth

Authentication & Access Control

Login

Email and password. Only @alec.ae addresses are accepted at registration. Passwords hashed with bcrypt. Sessions are cookie-based using itsdangerous.URLSafeSerializer with a server-side secret key. No OAuth or SSO integration.

Role Model

Two roles: Owner (oawad@alec.ae) and Admin. Owner sees all projects, manages the registry, holds shared Forma credentials, and can access all pending submissions and invite logs. Admins are strictly scoped to their listed projects.

Route Guards

require_user validates the session cookie and rejects unauthenticated requests with a redirect to /login. require_owner additionally checks the authenticated email equals OWNER_EMAIL. Both are applied as FastAPI Depends() arguments.

Public Routes

/login and /portal/platformAccess with its two POST endpoints (/submit and /submit/single) are publicly accessible with no authentication required. The portal is the only intentionally public surface of the system.

Security The SECRET_KEY used for session signing is currently hardcoded in app.py. It should be moved to an Azure App Service environment variable. The users.json file in blob is the only persistence layer for credentials — there is no database.

Web App

Web Application — app.py

app.py is a single-file FastAPI application of approximately 2,800 lines. It serves the browser UI via Jinja2 templates, exposes a REST API consumed by frontend JavaScript, calls platform APIs directly for invites and user search, and launches extraction scripts as managed subprocesses. All blob reads and writes use the azure-storage-blob SDK with a connection string from the environment.

Frontend Architecture

The frontend is server-rendered HTML (Jinja2) with progressive JavaScript enhancement. There is no frontend build step or bundler. base.html provides the sidebar, navigation, and project context selector. It dispatches a cockpit:projectChanged CustomEvent on window whenever the active project changes — child pages listen to this event to reload their content without a full page refresh. static/utils.js provides the hacker-text scramble animation and local cache helpers.

07
Platforms

Platform Integrations

Revizto

API Endpoints

Two regional servers: api.dubai.revizto.com/v5 and api.ireland.revizto.com/v5. The active region is resolved from active_context.revizto_region in the admin's config. Each admin authenticates with their own access code. Tokens are cached per-region per-admin in blob as revizto_tokens_{region}_{email}.json.

Auth Flow

Access code submitted to POST /oauth/access-code/token to obtain a bearer token (approximately one hour expiry). The token is cached to blob. On expiry, a refresh is attempted automatically using the cached refresh token. License UUID is resolved once via GET /user/licenses and stored in config.

Invite Flow

Two-step operation: (1) add user to the license via POST /license/{uuid}/member/invite, (2) optionally assign a project role via POST /project/{uuid}/role/member/invite. The "Invite to license" and "Invite to project" toggles in the UI control which steps execute. License Admin (role id 4) is blocked across all UI surfaces.

Registry Sync

Project roles fetched via GET /project/{uuid}/role/list and stored under platforms.revizto.roles. License roles (Guest, Collaborator, Content Creator) are hardcoded — they do not require an API call and are always written to the registry on sync regardless of token availability.

Morta

API

api.morta.io/v1. Authenticated with a personal API key set per-admin in Settings. The key is permanent — no token refresh required. There is no owner fallback for Morta. If an admin has not configured their Morta API key, Morta features (search, invite, extraction) are unavailable to them.

Invite Flow

POST /hub/{hub_id}/member/invite. A permission tag can be assigned in the same call by passing tag_reference_id. Tags are synced into the registry from GET /hub/{id}/tags during the registry sync operation and presented as a dropdown in the invite UI.

Search

Members fetched from GET /hub/{hub_id}/members and matched by email. Search is scoped to the hub IDs of the admin's registry projects only. Tags assigned to the matched user are extracted from the member record and returned in the search result.

Extractions

Hub Members (Morta_GET_members), Permission Tags (Morta_GET_Tags), Hub Admins (Morta_GET_Admin). Output written to temp/{email}/ as both CSV and JSON.

Forma / ACC — Autodesk

Auth

Two flows in parallel: 2-legged (client_credentials grant) for account-level operations (hub users, project management), 3-legged (user OAuth) for model-level access requiring user context. The 2L token is cached as forma_tokens.json in blob. Credentials are shared — all admins inherit from the owner config.

Invite Flow

Account-level: POST /hq/v1/accounts/{id}/users/import. Project-level: POST /construction/admin/v1/projects/{id}/users. A single invite call can specify company, role, and product access levels (Docs, Design Collaboration, Model Coordination) simultaneously.

Registry Sync

Companies fetched via GET /hq/v2/accounts/{id}/companies. Project roles fetched via GET /construction/admin/v1/projects/{id}/role-templates. Both stored in the registry under platforms.forma.companies and platforms.forma.roles. Always uses owner credentials.

Extractions

Account Projects, Hub Users, Project Files, Project Models, Model Properties (2L and 3L auth modes), Processed Model Properties. The Forma_MasterScript.py handles token acquisition and stores the result to blob under the COCKPIT_USER namespace.

Scripts

Script Layer

All data extraction logic lives in standalone Python scripts. They can run directly from a terminal in local development, or be triggered by the web app as managed subprocesses in production. Each script imports its platform config module (*_Config.py) which reads the merged config from COCKPIT_CONFIG and writes output to COCKPIT_EXPORTS_DIR. Internal files starting with _ are excluded from the download list presented to the user.

Flows

Key Data Flows

Portal Submission — Subcontractor to Platform Access

1
Subcontractor opens portal URLURL contains ?pid=project-key. The project name is resolved from GET /api/registry and displayed in the project badge. No login required.
2
Submits access requestBulk mode: uploads an Excel file with user data. Single mode: fills in name, email, company, department, and platform checkboxes. Submitter fields are not duplicated — the person requesting access for themselves is the submitter.
3
Server parses and stores the submissionBulk: Excel parsed with openpyxl. Both modes write a structured submission record to portal_requests.json in blob, keyed by project ID. Each user entry has status pending.
4
Email notification dispatchedAll emails in the project registry's admins[] array receive an HTML notification via Azure Communication Services. The email contains a direct link to /manage.
5
Admin opens Manage Users — Pending SubmissionsSubmissions are filtered to the active sidebar project. Submission status: pending (awaiting action) / processed (all users done) / rejected (all users declined) / partial (mix).
6
Admin reviews and configures accessExpandable panel shows each user. Admin adjusts Morta tag, Revizto license role, Revizto project role, Forma company, and Forma role. All dropdowns are populated from the registry — no live API call at this stage.
7
Process invitationsServer calls Morta, Revizto, and Forma APIs per the configured access. Each platform invite is attempted independently — a failure on one does not block the others. Results per user are recorded with success, skipped, or error status.
8
Logged to invite_log.jsonEach processed user is appended to invite_log.json in blob with date, mode, platform statuses, project key, and user details. Visible in the Invite Log card scoped to the active project.

Extraction Run — Script Subprocess

1
Admin selects a script and clicks ExtractExtractions page sends POST /api/extract with the script name and active context. The active project must be set in the sidebar.
2
build_script_config() assembles the runtime configMerges the admin's personal credentials with the owner's shared Forma block. Writes the merged object to temp/{safe_email}/_cockpit_config.json.
3
Subprocess launched with environment variablesCOCKPIT_CONFIG, COCKPIT_EXPORTS_DIR, and COCKPIT_USER are injected into the subprocess environment before launch. The script file path is resolved at startup time.
4
Script executes against the platform APIThe platform *_Config.py module reads COCKPIT_CONFIG. The script calls the appropriate endpoints, writes CSV and JSON to COCKPIT_EXPORTS_DIR, and prints progress to stdout.
5
Web app streams output and serves download linksStdout lines are captured and returned to the browser. Files in temp/{email}/ not starting with _ are listed as download links. Files persist until manually cleared or cleaned up after 24 hours.

Registry Sync — Live Platform Data

1
Admin clicks Sync on a registry projectTriggers POST /api/registry/project/{key}/sync. Any authenticated user who is an admin of that project can initiate a sync.
2
Morta tags fetchedUses the syncing admin's Morta API key. If not configured, falls back to the owner's API key. Tags written to platforms.morta.tags[].
3
Revizto project roles fetchedUses the admin's token. License roles (Guest, Collaborator, Content Creator) are always written regardless of API result. Project roles require a valid token and accessible project UUID.
4
Forma companies and roles fetchedAlways uses owner credentials — Forma sync never uses individual admin credentials. Companies and project role templates are written to the registry.
5
Registry written to blob storageUpdated projects_registry.json is serialised and written to blob. All admins of that project immediately see the updated tags, roles, and companies in their invite forms on next page load.
