01Overview

What this is, and the bet behind it

A single-process FastAPI server that orchestrates user provisioning, data extraction, and scheduled automation across three construction platforms — Revizto Morta Forma / ACC — for an entire engineering organisation.

The Cockpit consolidates work that previously required three separate consoles, three separate sets of admin credentials, and a permanent stream of manual user-management tickets. It runs on a single Azure App Service B1 instance in West Europe, serves the entire ALEC organisation, and keeps every byte of runtime state in Azure Blob Storage so the application process can be restarted at any moment without losing anything.

The four design bets

Every architectural choice in the system traces back to one of four deliberate bets. Understanding these makes the rest of the design read as a single coherent argument rather than a collection of features.

1 · Stateless process, externalised state

The FastAPI process holds no durable state in memory. Sessions, tokens, configs, scheduler shards, run history — all of it lives in blob storage. The application can be killed and restarted in seconds with zero data loss, and deployments don't require migration scripts. Cost: every state read costs a blob fetch (mitigated with in-process LRU caching and write-through invalidation). Benefit: the system is restart-safe by construction.

2 · Per-admin namespacing instead of multi-tenancy

The Cockpit serves dozens of admins from one process without spinning up per-tenant resources. State is namespaced by safe-email (e.g. config_oawad_at_alec_ae.json, revizto_tokens_dubai_oawad_at_alec_ae.json). When Admin A's tokens expire, it doesn't affect Admin B. Project access is gated by registry membership, not URL routing. Cost: careful key design and a single invariant — every blob write must include the admin's safe-email in the key. Benefit: no Postgres, no auth server, no tenant isolation infrastructure.

3 · Subprocess-as-script, not embedded library

Platform integrations (every Revizto/Morta/Forma extraction) run as child Python processes spawned with environment-injected configs. The same scripts that the Cockpit dispatches can be run unchanged from a developer's VS Code, or invoked by the scheduler. Cost: subprocess overhead and stdout streaming through SSE. Benefit: manual, scheduled, and developer-driven runs share their entire code path. One fix lands everywhere.

4 · Pull, never push, for the firewall

ALEC's BIM coordinator laptops sit behind a corporate firewall with no inbound connectivity. The Cockpit cannot push to them. Instead, the optional cockpitAgent daemon polls /api/agent/work on a 30-second loop, claims unfinished runs, and writes outputs to a configured local path. Cost: ~30s delivery latency. Benefit: zero corporate-network changes required to onboard a new machine.

What you should remember leaving this chapter

The Cockpit is an exercise in extracting maximum operational depth from minimal infrastructure. One Azure compute instance, one storage account, four blob containers. The architecture compensates for that minimalism with disciplined namespacing, deliberate statelessness, and a strict separation between the orchestrating web layer and the platform scripts that do the actual API work. Each subsequent chapter explains one of those disciplines in detail.

02State

The stateless process and its externalised state

The FastAPI process holds nothing durable. Every byte of runtime state lives in blob storage, namespaced for safe concurrent access by dozens of admins.

The invariant

The Cockpit's master invariant is process-restart-ability. At any instant, the process can be killed, redeployed, or moved to another region, and on next request a previously logged-in admin must see exactly what they saw before — same active project, same pending submissions, same scheduled shards, same recent runs. This is achievable only because no fact about the system lives in the process. The process is a stateless interpreter for a state machine whose only durable representation is a set of JSON blobs.

The trade-off is explicit: every read costs a blob fetch. To keep this affordable on the B1 tier (single CPU, 1.75 GB RAM), the system uses a write-through in-process LRU cache via codeShared/Blob_Client.py. Reads hit memory after the first call; writes update both memory and blob synchronously. Cache invalidation is straightforward because there is no cross-process coordination — only one process exists.

The diagram below identifies every persistent blob the system writes, what feature owns it, and the access pattern. Read this as the complete set — there is no other persistent state.

Why this works on B1

The B1 tier provides 1.75 GB RAM and a single CPU core. Naively reading every blob on every request would be unacceptable — the cockpit-data container holds dozens of files and a typical page load touches several. The mitigation is two-layered:

  • In-process LRU cache. Blob_Client.py exposes load_json(key) which checks a dict first, fetches from blob on miss, and stores the result with a short TTL (typically 60s, configurable per-call). Cache hits are zero-network and microsecond-fast.
  • Write-through invalidation. save_json(key, data) writes blob first, then updates the in-process cache with the new value. There is no cache-invalidation race because writes update both the source-of-truth and the cache in one synchronous step.
  • No cross-process coordination. Because exactly one process owns the cache, no Redis, no etcd, no distributed lock. If we ever scale to multiple workers, the cache becomes incorrect — that's a known constraint and one reason the system stays on B1's single instance.

What's NOT in blob

Three categories of state intentionally don't live in blob:

Session cookies

Signed with SECRET_KEY from the App Service environment. Hold only the user's email. No DB. On restart, valid cookies still validate — the secret survives.

Subprocess temp files

Per-run merged configs and intermediate L3 outputs land in /tmp/_scheduler/{run_id}/ on the App Service filesystem. Lost on restart by design — runs in flight die with the process.

APScheduler in-memory state

The cron registry is rebuilt from compilers.json on every process start. APScheduler itself holds no durable jobs — it's a thin in-process executor.

Operational consequence An admin pressing "Restart" in the Azure portal results in zero data loss. Active subprocess runs are killed (their runs.json entry remains in running status until manually pruned), but no shard, compiler, token, or config is ever damaged. Deployments are similarly safe — they're atomic from blob's perspective.
03Auth

Multi-tenant identity and the merged config contract

Three platforms, three completely different auth models, one consistent ergonomic for the scripts that consume them.

The problem

Each external SaaS the Cockpit integrates with has its own opinion about authentication. Revizto demands an admin-issued access code which the Cockpit exchanges for short-lived bearer tokens, refreshable until the underlying refresh-token expires. Morta uses a static personal API key with no refresh story. Autodesk Forma uses two flavours of OAuth — 2-legged client_credentials for account-wide reads, 3-legged user-OAuth for model-level operations — sharing the same client_id but resolving to different token caches. The naive approach would be to thread three different auth machines through every script. The Cockpit instead reduces all three to a single contract.

The contract: COCKPIT_CONFIG

Every platform script reads exactly one environment variable: COCKPIT_CONFIG, the path to a JSON file. That file holds, for the executing admin, all credentials and active context the script needs. The script does not know — and does not care — where those credentials came from, whether they're personal or fallback, or whether they had to be refreshed. The script's job is to read the config, call the platform API, and write outputs. The Cockpit's job is to make sure the config in that file is correct at the instant the subprocess starts.

// /tmp/oawad_at_alec_ae/_cockpit_config.json — written by build_script_config()
{
  "morta": { "api_key": "abc123..." },
  "revizto": {
    "region":       "dubai",
    "access_code":  "…",
    "tokens_path":  "revizto_tokens_dubai_oawad_at_alec_ae.json"
  },
  "forma": {
    "client_id":    "…",        // from owner if missing in user's
    "client_secret": "…",
    "account_id":   "…",
    "last_runs": { ... }      // L3 stamps for L4 dependency
  },
  "active_context": {
    "active_project_key":    "rak-central",
    "revizto_project_uuid":  "…",
    "morta_hub_id":          "…",
    "forma_project_id":      "…",
    "forma_model_item_id":   "…"     // only when scheduler runs L3/L4
  }
}

The merger: build_script_config()

The function build_script_config(user_email) in app.py is the only place the merger logic lives. Before any subprocess is spawned, this function executes the following resolution:

# Step-by-step config merge for an extraction or scheduled run

user_cfg     = load_config(user_email)               # config_{safe_email}.json
owner_cfg    = load_config(OWNER_EMAIL)             # config_oawad_at_alec_ae.json

merged = {
    "morta":   user_cfg.morta,                       # strict — no fallback
    "revizto": user_cfg.revizto,                     # strict — no fallback
    "forma":   user_cfg.forma or owner_cfg.forma,    # Forma falls back!
    "active_context": user_cfg.active_context
}

write_to_path(merged, f"/tmp/{safe_email}/_cockpit_config.json")
subprocess_env["COCKPIT_CONFIG"] = path

The asymmetry is intentional. Forma's 2-legged credentials are organisation-level, not personal — every admin uses the same client_id to invite users into the same Autodesk account. Putting that secret in every admin's personal config would be wasteful and a key-rotation nightmare. Instead, the owner's config holds the canonical Forma block, and the merger uses it as the fallback for any admin whose own config doesn't override. Revizto and Morta have no such fallback because their credentials are inherently personal — Revizto access codes are tied to specific user accounts, and Morta API keys grant the holder's individual permissions.

Per-platform auth deep dive

Revizto

An admin enters a region (dubai or ireland) and an access code in their Settings page. The Cockpit POSTs to /oauth/token on api.{region}.revizto.com exchanging the code for a bearer token (~60 minute TTL) and a longer-lived refresh token. Both are cached to revizto_tokens_{region}_{safe_email}.json. On every subsequent API call, revizto_get_token_for_region() in app.py checks the cache, refreshes if expired, re-exchanges via access code if the refresh token itself has expired, and returns the bearer. Scripts read the cache directly via Revizto_MasterScript.py, namespaced by COCKPIT_USER.

Morta

The admin pastes their personal API key into Settings. There is no exchange, no refresh, no cache file. The key is read directly from config_{safe_email}.json on every call and passed in the Authorization header. Morta's permissions are whatever the holder has — which means an admin's Morta credentials limit the project hubs they can read, regardless of what the Cockpit's registry says. This is by design: Morta is treated as a thin proxy for the admin's existing Morta account.

Forma — 2-legged (shared)

Used for: account-level operations, project lists, hub user listings, user invites, model-list walks. The owner's forma block holds client_id and client_secret. get_2legged_token() POSTs to /authentication/v2/token with grant_type=client_credentials, scopes data:read account:read user-profile:read, caches the result in forma_tokens.json (one file, shared across the whole Cockpit, no per-admin namespace). TTL ~1 hour. Refresh is automatic on next call after expiry.

Forma — 3-legged (per-admin)

Required for: anything that hits the Project Index API — model property extraction, in particular. Autodesk's Index API requires a user identity, not a service-account identity. The admin clicks "Connect to Forma" in Settings, gets redirected to Autodesk's authorize endpoint, grants consent, and lands back at /auth/forma/callback with an authorization_code. The Cockpit exchanges that for refresh + access tokens scoped data:read viewables:read account:read user-profile:read, and caches them in forma_3l_{safe_email}.json. The scheduler injects the path to this file into the subprocess via COCKPIT_FORMA_3L_TOKEN_FILE when running model-level scripts.

Owner-only territory

The owner (oawad@alec.ae in this deployment) has one capability no other admin has: editing the Forma block in Settings. For every other admin, the Forma section of Settings is read-only and shows whatever the owner's config provides as a fallback. This concentrates the secret-management burden in exactly one place. Revoking an admin's Forma access amounts to not giving them a personal forma block; they automatically inherit the owner's. Granting them their own override is a deliberate per-admin act.

Security invariant Scripts never see the owner's config directly. They only ever see the merged JSON written to their own /tmp/{safe_email}/_cockpit_config.json. Even if a script were compromised, it could not enumerate other admins' credentials — its config file contains only one identity's worth of secrets. The owner's config never leaves the FastAPI process boundary.
04Execution

The execution layer — how things actually run

A single subprocess pipeline serves four entry points: Run-Now, ad-hoc Extractions, scheduled Compiler fires, and dependency-chained L4 reports. Same code path. Same observability. Same failure modes.

The script pipeline

Every platform script runs as a child Python process. The pipeline is deliberately uniform across all four entry points so that fixes, observability hooks, and resource limits land in one place. The runner that orchestrates it lives in codeShared/Scheduler_Runner.py and is also imported by the live extraction streamer in app.py.

The scheduler model

Three nested concepts make scheduled automation work without coupling cron logic to data:

Shard

An atomic runnable unit. Holds: script name, platform, full context (project_id, model_id where applicable), output config (formats, prefix, naming flags, custom_name), and optional destination.local_path for cockpitAgent. Saved with a snapshot of the active project at save time so retargeting requires deletion + recreation.

Compiler

A schedule wrapper. Holds: cron expression (or daily/weekly/monthly preset), list of shard IDs, active flag. When cron fires, the engine looks up the compiler's shards and dispatches each through Scheduler_Runner.run_shard() sequentially.

Run

A historical execution record. Holds: shard ID, status, kind (manual/scheduler/compiler), exit_code, stdout_tail (last 50 lines), output_blobs (with byte sizes), parent_compiler_run_id (for nested runs), delivery_state for agent pulls.

Cron firing engine

The engine in codeShared/Scheduler_Engine.py uses APScheduler's BackgroundScheduler with a thread pool. On app startup, it reads all compilers from blob and registers a CronTrigger for each active one. When a trigger fires, the engine creates a parent compiler-run record and dispatches each shard sequentially through the same Scheduler_Runner.run_shard() the manual Run-Now button uses. Cron-fired runs and manual runs share their entire code path; the only difference is the kind field on the run record.

Single-instance assumption APScheduler is in-process and single-instance. The B1 plan runs one worker, so this is fine. If the Cockpit ever scales to multiple workers, the engine would need a distributed lock to prevent duplicate fires. This is a known constraint, not a bug.

L3 → L4 dependency chain (the 24h cache)

The most architecturally interesting execution path. Some scripts (currently just Proccesed_Model_Properties, the L4 model health report) require the output of another script (the L3 Forma_GET_Model_Properties) as input. Naively, the user would have to run L3 manually, then L4. For ad-hoc work this is fine — for scheduled automation it's broken.

The runner solves this in _ensure_l3_prerequisite() before each run. The decision tree:

# Pseudo-code — _ensure_l3_prerequisite() in Scheduler_Runner.py

if shard.script in L4_DEPENDENCIES:
    prereq          = L4_DEPENDENCIES[shard.script]["requires"]   # e.g. Forma_GET_Model_Properties
    model_id        = shard.context.model_item_id                # SHARD's context, NOT user's sidebar
    last_stamp      = user_config.forma.last_runs[prereq]

    if last_stamp.context_value == model_id and age(last_stamp) < 24h:
        # Cache hit — find prior L3 output files on disk, copy into this run's /tmp
        copy_cached_l3_files(last_stamp.files, run_temp)
    else:
        # Cache miss — run L3 inline, in the same /tmp dir L4 will use
        result = run_subprocess_for_l3(prereq, ...)
        if not result.ok:
            return {"status": "failed", "error": f"L3 prerequisite failed: {result.error}"}
        stamp_l3_run(user, prereq, result.files)   # write to last_runs for future cache

# Then proceed normally — L4 reads L3's outputs from the same temp dir

The 24-hour cache window matters. A common workflow is to run 15 different L4 reports against the same model in sequence — under the cache, the L3 fetch (which can take minutes for a 100k-element model) happens exactly once. Without the cache, every L4 would re-fetch.

Manual extractions vs. scheduled runs

The /api/extract/stream endpoint is a thin SSE wrapper around Scheduler_Runner. The shape of a "shard" is constructed on the fly from the Extractions page form input — same downstream pipeline. The only divergence is observability: manual runs stream stdout to the browser as it happens; scheduled runs capture stdout to the run record's stdout_tail field. Identical engine, identical config merge, identical subprocess spawn.

05cockpitAgent

cockpitAgent — solving the firewall with claim-based delivery

A 250-line Python daemon that turns the Cockpit into a viable replacement for in-house file-server scripts, without touching the corporate network configuration.

Why this exists

BIM coordinator workflows depend on outputs landing in specific local folders. A weekly model health report needs to appear in a Revit-readable directory by 9am Monday so the morning sync routine picks it up. A monthly clash export needs to land on a Power BI ingestion folder. Both targets sit on machines inside ALEC's corporate network, behind a firewall that has no inbound port forwarding for the App Service. The Cockpit cannot push.

The alternatives — IT-approved webhooks, FTP from the App Service to corporate file shares, scheduled emails with attachments — were either operationally heavyweight, or rejected at the security review stage. The chosen pattern flips the direction: every machine that needs files polls the Cockpit. This requires zero network changes because polling uses the same outbound HTTPS that the rest of corporate Internet traffic uses.

The token model

Each laptop gets a unique token, scoped to the issuing admin and labelled for that machine ("Omar's laptop"). Tokens carry an install_date_iso field set at issuance time. When a scheduled run finishes and is destined for a local path, the Cockpit only offers it to agents whose install_date_iso predates the run's start time. This single gate prevents a freshly issued token from being handed an enormous backlog of historical runs the new machine has no business pulling.

// agent_tokens.json — one entry per laptop
{
  "token":            "ckpt_5f7a3b2c...",    // shown ONCE on creation
  "label":            "Omar laptop",
  "owner_user":       "oawad@alec.ae",
  "install_date_iso": "2024-04-20T10:00:00Z",
  "created_at":       1714780000,
  "last_seen_at":     1714820000,    // updated every poll
  "last_ip":          "10.13.4.22"
}

Delivery state machine

Every run record carries a delivery_state field whose value is the source of truth for whether that run's outputs have been picked up by an agent. The state machine has four states and two transition rules:

Transition A is the claim. The endpoint POST /api/agent/work finds the oldest run with destination.type=blob, non-empty destination.local_path, status success, and delivery_state=pending, atomically updates its delivery_state to claimed_by:{token_id} with the current timestamp, and returns SAS-signed download URLs for the run's output files. If two agents poll at the same instant — say Omar's laptop and a colleague's — only one's claim succeeds. The other receives {work: null} and continues its poll loop.

Transition B is delivery confirmation. After downloading and writing the files, the agent calls POST /api/agent/done with the run ID and the byte count. The server marks delivery_state as delivered with the completion timestamp. The Recent Runs UI flips the badge from "pending" to a green check.

Transition C is stale-claim recovery. If an agent crashes mid-download — disconnects, runs out of disk, hits an unrecoverable I/O error — its claim is held forever and no other agent picks the run up. The reaper logic on every poll checks: if any claim is older than 10 minutes and not delivered, reset its delivery_state to pending so another agent can try. This makes the system self-healing without manual intervention.

What the agent looks like

The agent itself is intentionally minimal. ~250 lines of Python that:

  1. Reads config.ini for its token + Cockpit URL
  2. Loops every ~30 seconds, polling POST /api/agent/work
  3. If work returned: fetches the SAS URLs, writes files to the per-run destination.local_path, preserving filenames
  4. POSTs /api/agent/done with the byte count
  5. Logs every action to a local log file for debugging

It's distributed as a cockpit-agent.py source file with a config.ini.example template and a plain-text README. Recipients install Python 3, run pip install requests, fill in their config, and either run the script in a terminal or register it as a Windows Task Scheduler entry. There is no installer, no update mechanism, no telemetry. Updates are manual — the agent's API surface is small enough that breaking changes are rare.

The compiler-only delivery rule

One subtle but important rule: only runs fired by a compiler trigger agent delivery. A manual single-shard Run-Now does not, even if the shard has a local_path set. The reasoning: if an admin clicks Run-Now, they're at their desk, watching the run, and they want to download the output via the browser when they need it. Agent delivery is for unattended automation — the things that should land on a colleague's machine while they're on leave. Conflating the two would have agents racing the browser to download exports the admin is already pulling manually.

Vacation continuity The original motivation was vacation continuity. When an admin goes on leave, their scheduled extractions still need to land on the team's shared drive. Issuing a token to a colleague's machine before leaving means scheduled runs continue without intervention — the colleague doesn't need Cockpit credentials, just a token whose install_date_iso predates the leave date. This single use case justified the entire claim-based delivery design.
06Surface

The user-facing surface

Project-scoped views, two-channel context propagation, and a public access portal that converts subcontractor requests into multi-platform invites in one click.

The active project as universal scope

Every meaningful action in the Cockpit happens in the context of one project. The user search is scoped to it. The invite log is scoped to it. The pending submissions queue is scoped to it. Scheduled shards snapshot it. The active project — selected once in the sidebar — is the universal scope variable, and the system propagates it through two complementary channels.

The two-channel design is deliberate. Without the event, switching project in the sidebar wouldn't update an already-open Extractions page until manual reload — and an admin would happily run scripts against a stale active project not realising they'd switched. Without the HTTP write, opening a new tab would forget the sidebar's choice. The two channels are complementary, not redundant.

The portal: turning subcontractor requests into invites

Subcontractors who need access to ALEC's projects on Revizto/Morta/Forma have, historically, asked someone over email. The portal at /portal/platformAccess formalises this: a public, no-account-required form where they enter their company, the project, the platforms they need, the role they need on each, and (where relevant) the company affiliation that determines their permissions. They can submit single requests, or bulk-upload a CSV with multiple users.

Submissions land in portal_requests.json as pending entries scoped per project. An admin's Manage Users page surfaces these in the Pending Submissions panel, scoped to whatever project is currently active. The admin reviews, optionally edits the platform-specific fields, and clicks "Process" — which fires the same inline invite functions a manual invite uses, marking the submission as processed and writing entries into the invite log. One click goes from "subcontractor wanted access" to "user is invited on every platform they need".

Public submission flow

Subcontractor visits /portal/platformAccess. No login required. Picks the project (only those marked public-facing in the registry are listed). Fills the form: contact info, platform toggles (Revizto / Morta / Forma), per-platform role selections, company affiliation. Submits via POST /portal/platformAccess/submit. Receives an email confirmation via Azure Communication Services.

Admin processing flow

Admin opens Manage Users. The Pending Submissions panel lists all submissions scoped to the active project. Each row exposes the original submission's read-only company/dept fields plus 19 editable cells mirroring the live invite form. Admin edits where needed, clicks Process. The processor fires forma_invite(), revizto_invite(), morta_invite() as toggled, writes invite-log entries, marks the submission processed.

Manage Users — the consolidated control plane

The Manage Users page is where most admin work happens. It exposes four operations on a single screen:

  • User search — looks up a user across all three platforms by email. Results show the user's current state on each platform: what role they have on Revizto, what tags on Morta, what company/role on Forma. Calls hit the live platform APIs (cached briefly).
  • Single-user invite — a 21-cell form (Email + 20 platform-specific fields) that fires the three inline invite functions. Each cell knows whether it applies to which platform; toggling off a platform fades its cells.
  • Bulk invite via CSV — paste a CSV, preview parsed rows, fire as a batch. Each row's failures are reported individually; one bad row doesn't kill the batch.
  • Invite log — append-only history scoped to the active project. Each entry records which admin ran the invite, what was attempted on each platform, and the per-platform success/failure.
  • Pending submissions — the portal queue, processable inline.

Settings, Registry, Profile

Three smaller pages round out the surface. Settings is where admins paste their personal credentials (Revizto access codes, Morta API key) and connect Forma 3-legged. Registry is owner-only — the master list of projects with their platform IDs, admin lists, tag mappings, and role definitions. Profile shows per-admin invite stats and recent activity, and is the only page where an admin can see their own historical contribution.

Live Activity feed

The home dashboard's Live Activity feed reads invite_log.json filtered to the active project and shows the last N invite events with admin attribution and timestamps. It updates in real time when a new invite happens in the same tab (via the cockpit:inviteLogged event), and refreshes on page load otherwise. It's the closest thing the system has to an audit trail.

7.2 · Blob storage — every key, every schema

Five containers in storage account cockpitdatastorage. Container cockpit-data holds JSON state with indefinite retention. The four {platform}-exports containers hold extraction outputs with a 15-day lifecycle policy that auto-deletes blobs older than 15 days.

cockpit-data — state files

users.json
Admin accounts. { users: [{ email, password_bcrypt, role, created_at }] }. Role is "owner" or "admin". Owner is hardcoded by email match in OWNER_EMAIL env var; the role here is informational.
projects_registry.json
Master project list. { projects: { "{key}": { name, admins: [emails], revizto: {region, project_uuid}, morta: {hub_id, tags: [...]}, forma: {project_id, account_id, companies: [...], roles: [...]}, public_facing: bool } } }. Owner-only writes via /api/registry/*. Admins read-only via /api/projects (filtered to their membership).

Per-admin per-region cached Revizto tokens. { access_token, refresh_token, expires_at, refreshed_at }. Refreshed automatically by revizto_get_token_for_region() in app.py on expiry. forma_tokens.json
Single shared 2-legged Forma token. { access_token, expires_at, refreshed_at }. ~1h TTL. NOT namespaced per admin — every admin uses the same cached token because 2-legged is application-level. Refreshed automatically on next call after expiry.
forma_3l_{safe_email}.json
Per-admin 3-legged Forma OAuth tokens. { access_token, refresh_token, expires_at, refreshed_at, scope }. Acquired via /auth/forma/start → callback OAuth dance. forma_models_cache.json
Per-project Forma model lists. { "{project_id}": { models: [{id, name, path, parent_folder}], cached_at } }. Populated by POST /api/forma/models which walks the project's folder structure. The "Shared" folder filter is enforced server-side. Force-refreshes on demand via the same endpoint with refresh=true.
shards.json
Scheduler shards. { shards: [{ id, name, owner_user, platform, script, context: {...}, output: {formats, prefix, naming, custom_name}, destination: {type, local_path?}, active, in_compiler, created_at, consecutive_failures, auto_disabled }] }. Context snapshots project_id/model_id/project_name at save time so historical runs aren't affected by registry changes.
compilers.json
Scheduler compilers. { compilers: [{ id, name, owner_user, schedule: {kind, cron|preset}, shard_ids: [], active, created_at }] }. APScheduler reads this on startup and registers a CronTrigger per active compiler.
runs.json
Run history. { runs: [{ id, kind: "shard"|"compiler", shard_id?, compiler_id?, parent_compiler_run_id?, owner_user, started_at, finished_at, status: "running"|"success"|"failed"|"partial", exit_code, stdout_tail: [], output_blobs: [{filename, size_bytes, blob_url}], destination: {...}, delivery_state: "pending"|"claimed_by:{tid}"|"delivered", claim_timestamp?, delivery_timestamp?, error? }] }. Append-only with periodic prune (manual). Compiler runs are parent rows; child shard runs reference them via parent_compiler_run_id.
agent_tokens.json
Per-machine cockpitAgent tokens. { tokens: [{ id, token_prefix, token_bcrypt, label, owner_user, install_date_iso, created_at, last_seen_at, last_ip, revoked }] }. The plaintext token is shown ONCE on creation and never stored — only its bcrypt hash and a 12-char prefix for UI identification. Auth lookup hashes the incoming token and compares.
invite_log.json
Append-only invite history. { entries: [{ id, project_key, admin_user, target_email, target_company, target_dept, platforms: {forma: {ok, error?}, revizto: {ok, error?}, morta: {ok, error?}}, source: "manual"|"portal"|"bulk", portal_submission_id?, timestamp }] }. Powers Live Activity feed and the invite log table on Manage Users.
portal_requests.json
Pending portal submissions. { "{project_key}": [{ submission_idx, submitted_at, contact: {name, email, company, dept}, requested_platforms: [], requested_role_revizto?, requested_tag_morta?, requested_company_forma?, requested_role_forma?, status: "pending"|"processed"|"rejected", processed_by?, processed_at? }] }. Indexed by project key for fast scope filtering on Manage Users.
packages.json
Bake feature — saved snapshot manifests. { packages: [{ id, name, owner_user, created_at, files: [{filename, blob_url, size_bytes, run_id?}] }] }. Orthogonal to the run lifecycle; admins explicitly bake a set of files into a named package for later retrieval.

{platform}-exports — extraction outputs

Containers forma-exports, morta-exports, revizto-exports, scheduler-exports. All have a 15-day lifecycle rule that auto-deletes blobs older than 15 days. Naming convention is {run_id}/{filename} for scheduler-exports, or {safe_email}/{timestamp}_{filename} for direct extractions. Files are accessed via SAS-signed URLs generated at request time, never via static URLs.

7.9 · cockpitAgent token authentication internals

Tokens are issued as ckpt_{32-char-random}. The plaintext is hashed with bcrypt and only the hash is stored. The first 12 chars of the plaintext (e.g. ckpt_5f7a3b2c) are stored separately as token_prefix for UI identification. On every agent request, the server iterates active tokens and bcrypt-compares the incoming bearer against each hash. This is O(N) per request where N is the number of active tokens — currently small enough that the constant factor of bcrypt dominates linear scan cost.

Token revocation does not delete the row — it sets revoked: true. The auth lookup skips revoked tokens. This preserves historical attribution for runs that were claimed by a now-revoked token.

The install_date_iso gate works at run-claim time, not token-validation time. A revoked token that's reissued with a new install_date won't suddenly see runs that happened before its new install date. This is enforced in the SQL-like predicate inside POST /api/agent/work:

SELECT runs WHERE
  status              = 'success'
  AND destination.type    = 'blob'
  AND destination.local_path IS NOT NULL AND != ''
  AND delivery_state      = 'pending'
  AND kind                = 'shard'
  AND parent_compiler_run_id IS NOT NULL   -- only compiler-fired runs
  AND started_at         >= token.install_date_iso
ORDER BY started_at ASC
LIMIT 1;

7.10 · APScheduler engine details

Configured in codeShared/Scheduler_Engine.py. Uses BackgroundScheduler with a thread pool executor (default size 10). On startup:

  1. load_compilers() reads compilers.json from blob
  2. For each active=true compiler, builds a CronTrigger from its schedule
  3. Registers the trigger with scheduler.add_job(fn=fire_compiler, trigger=cron, args=[compiler_id])
  4. fire_compiler(compiler_id) reloads the compiler (in case it was edited), creates a parent compiler-run record, then sequentially runs each shard via Scheduler_Runner.run_shard()

The scheduler hot-reloads on changes — POST/PUT/DELETE on compilers triggers scheduler.reschedule_job() or add_job()/remove_job() as appropriate. Pause toggles set active=false in blob and call scheduler.remove_job(); resume reverses both.

Schedule formats accepted by the API:

{ kind: "cron", cron: "0 6 * * 1-5" }
Raw cron expression. Five fields: minute hour day-of-month month day-of-week. Above example: 6 AM Monday-Friday.
{ kind: "preset", preset: "daily", hour: 6, minute: 0 }
Daily at the given time
{ kind: "preset", preset: "weekly", weekday: 1, hour: 6, minute: 0 }
Weekly. weekday 0=Sunday, 1=Monday, ..., 6=Saturday.
{ kind: "preset", preset: "monthly", day: 1, hour: 6, minute: 0 }
Monthly on the given day-of-month

Located in Scheduler_Runner._apply_output_filters_and_rename(). Applies four naming flags from the shard's output field:

append_date
Appends _YYYYMMDD from run_started_at
append_time
Appends _HHMMSS from run_started_at
include_project_name
Inserts a sanitized project name. Sanitization: re.sub(r'[^A-Za-z0-9_\-]+', '_', name).strip('_'). Read from shard.context.project_name snapshot.
overwrite_latest
Writes a SECOND copy without the timestamp suffixes (e.g., {base}_latest.csv). Useful for downstream consumers that always want "the most recent" without parsing dates.

Composed pattern: {prefix}{base}{_project_name}{_YYYYMMDD}{_HHMMSS}.{ext}. The base is custom_name if set, otherwise the script's original output filename. Format filtering happens before renaming — files with extensions not in output.formats are dropped first.

7.12 · Deployment

The deployment pipeline is git-based. There is no CI/CD; deploys are manual, atomic, and fast (~30 seconds end-to-end). The standard sequence:

# From the repo root on the developer's machine
git add <files>
git commit -m "..."
git push origin main

# Build a deploy artifact: zip of the current HEAD only (no history)
git archive --format=zip --output=deploy.zip HEAD

# Push to Azure App Service
az webapp deploy \
   --resource-group digitalcockpit-rg \
   --name digitalcockpit-alec \
   --src-path deploy.zip \
   --type zip

App Service's Oryx build system detects the Python project on each deploy, runs pip install -r requirements.txt in a clean venv, and starts the app via startup.sh. The previous instance is replaced atomically — there's no rolling deploy. Brief unavailability (~5 sec) during the swap is acceptable.

7.13 · Glossary

Active project
The project the admin has selected in the sidebar. Universal scope variable for every project-aware view. Persisted in config_{safe_email}.json under active_context.active_project_key.
Active context
The full set of context the cockpit needs to act on the active project: project_key, plus the platform-specific IDs (revizto_project_uuid, morta_hub_id, forma_project_id) and any model selection. Persisted alongside the active project key.
Admin (vs. owner)
An admin is anyone with a session in users.json and an @alec.ae email. The owner is the single admin whose email matches OWNER_EMAIL — they additionally have registry write access and own the canonical Forma 2-legged credentials.
L3 / L4
Internal labels for Forma extraction layers. L3 = raw model property fetch from Autodesk's Index API. L4 = downstream report consuming L3's output. The dependency between them is encoded in L4_DEPENDENCIES.
Shard
A scheduler atomic unit — script + context + output config + optional local-path destination. Self-contained: a shard knows everything needed to run itself.
Compiler
A scheduler cron wrapper. Holds a schedule expression and a list of shard IDs. When the cron fires, all referenced shards run in sequence.
Run
A historical execution record. Includes status, output blobs, stdout tail, and (for compiler-fired runs) the parent_compiler_run_id linking it to its compiler run.
cockpitAgent
The off-process Python daemon that polls the cockpit for runs destined for local file paths. Uses per-machine bearer tokens. See chapter 5.
2-legged Forma
Autodesk OAuth flow using grant_type=client_credentials. Application-level identity. Used for account/project/user APIs.
3-legged Forma
Autodesk OAuth flow using grant_type=authorization_code with a per-user authorize redirect. User-level identity. Required for the Index API (model properties).
Stamp
A record in config.forma.last_runs[script] noting that a script ran successfully against a specific context value at a specific time, and what files it produced. Used by the L3→L4 dependency cache.
safe_email
The admin's email transformed into a filename-safe form via email.replace("@","_at_").replace(".","_"). Used as a namespace component in every per-admin blob key.
SCRIPT_CATALOG
The canonical dict in app.py that lists every schedulable script with its platform, display name, and required context fields. Source of truth for the scheduler UI.
L4_DEPENDENCIES
The dict in app.py declaring which L4 scripts depend on which L3 scripts and what context field gates the dependency.
Bake / Package
Manual snapshot of a set of output files into a named, persistent bundle. Independent of the run lifecycle's 15-day cleanup.
Pending submission
A portal_requests.json entry that hasn't yet been processed into invites. Surfaced on Manage Users for the admins of the requested project.
Live Activity
The real-time invite event feed on the home dashboard. Reads invite_log.json filtered by active project. Updates in-tab via the cockpit:inviteLogged event.
