01
Overview

System Overview

The Digital Construction Cockpit is an internal web platform deployed at ALEC Holdings. It centralises three previously manual workflows: user invitations across construction tech platforms (Revizto Morta Forma / ACC), data extractions against those same platforms, and scheduled automations that fire extractions on cron and optionally deliver outputs to specific machines via a polling agent.

Five logical concerns make up the system. They share a single FastAPI process but interact through clean contracts so each can be tested and replaced independently:

Web layer

app.py serves Jinja2 templates and exposes the REST API. Holds session state in signed cookies and reads/writes blob storage. Roughly 7,500 lines.

Script layer

Standalone Python modules under codeRevizto/, codeMorta/, codeForma/. Each script runs as a subprocess invoked by the web layer with a per-admin merged config injected via env vars.

Scheduler engine

codeShared/Scheduler_Engine.py hosts APScheduler in-process. Reads compilers from blob, registers cron triggers, dispatches shards through the same runner the Run-Now button uses.

Active project context

Sidebar selection persisted to active_context in each admin's config. Propagates in-tab via the cockpit:projectChanged event; cross-tab via GET /api/context.

Laptop agent

cockpit-agent.py runs on a colleague's machine, polls /api/agent/work with a per-machine token, downloads claimed runs to a configured local path. Enables vacation continuity.

Persistence

Azure Blob Storage holds every runtime state object — credentials, registry, logs, token caches, scheduler state. The application process is fully stateless and restart-safe.

Three flows that show how the layers connect

The diagram below traces three common scenarios end-to-end. Each lane is a complete request: who triggers it, which server logic handles it, where it touches the outside world, and where the result lands. The flows differ in their timing characteristics — synchronous invites complete in seconds, extractions stream output for minutes, scheduled+agent flows are unattended and asynchronous — but they all share the same per-admin config merge and platform abstraction layer.

Registry

Project Registry

projects_registry.json in blob storage is the backbone of the entire access model. It maps a short project key to all platform identifiers, assigned admins, and live-synced metadata for that project. Every scoped operation in the system — what a user sees in the sidebar, what appears in search results, which tags and roles populate invite dropdowns — is derived from this file.

Registry sync (POST /api/registry/project/{key}/sync) fetches live data from each platform and writes it back. If the syncing admin has not configured their Morta API key or Forma credentials, the system falls back to the owner's credentials — except for Morta, where keys are strictly personal and no fallback is applied.

Access Rule Only oawad@alec.ae (owner) can create, update, or delete registry entries. Write routes use require_owner. GET /api/registry returns a user-scoped subset — non-owners only receive projects where their email appears in admins[].
04
Active Project

Active Project Context

The cockpit is heavily project-scoped. Almost every feature — the user search, invite log, pending submissions, extraction runs, scheduled shards — operates against one project at a time. The "Active Project" is the answer to "which project is this admin currently working with." It's chosen in the sidebar, persisted in the admin's config, and propagated to every page through both events and HTTP fetches.

Where it lives

The active project is stored under active_context in config_{email}.json. The shape contains the project key, display name, and the platform-specific identifiers needed to dispatch API calls without an extra lookup:

"active_context": {
  "active_project_key":    "rak-central",
  "active_project_name":   "RAK Central",
  "revizto_project_uuid":  "1cc01307-...",
  "revizto_project_name":  "RAK Central",
  "revizto_region":        "dubai",
  "morta_hub_id":          "406ed81a-...",
  "morta_hub_name":        "RAK Central",
  "forma_project_id":      "6bf6b4f6-...",
  "forma_project_name":    "RAK Central",
  "forma_platform":        "acc"
}

The two-channel propagation pattern

When the user picks a different project from the sidebar dropdown, two things happen in parallel: an HTTP POST /api/context persists the choice to blob, and a JavaScript cockpit:projectChanged CustomEvent fires on window with the new IDs. Pages already loaded react to the event and refresh their content without a full page reload. Pages loaded later read the truth from GET /api/context on init.

Event channel (in-session)

window.dispatchEvent(new CustomEvent('cockpit:projectChanged', { detail: {...} })). Fires only in the current browser tab. Listeners refresh in place — no reload, no flash. Used by Manage Users, Extractions, Scheduler, Home Live Activity.

HTTP channel (cross-session)

POST /api/context persists the chosen project. GET /api/context reads it back. Survives page reloads, browser restarts, and other devices. Validated server-side: a non-owner cannot set an active project they don't admin.

Why pages need both channels

Without the event, switching project in the sidebar wouldn't update an already-open Extractions page until the user manually reloaded — they'd run scripts against a stale active project and not realise. Without the HTTP write, opening a new tab would forget what the sidebar said. The two channels are complementary, not redundant.

Validation rules

The POST /api/context handler validates that non-owner admins are listed in admins[] for the project they're trying to activate. This prevents a malicious or buggy client from setting a project they shouldn't see. Owner is exempt — they can switch to any project.

Snapshot vs live Some surfaces snapshot the active project at action time (the scheduler bakes the project into a shard at save time — see Scheduler section), while others read it dynamically on each fetch (the Manage Users invite log re-fetches whenever the active project changes). The snapshotting choice is per-feature, not global.

Config System

Every admin has a personal config file in blob: config_{email}.json. The owner's config additionally holds the shared Forma/ACC credentials that all other admins inherit when their own are absent. Scripts never read from blob directly — they only read this temp file via the COCKPIT_CONFIG environment variable.

05
Auth

Authentication & Access Control

Login

Email and password. Only @alec.ae addresses are accepted at registration. Passwords hashed with bcrypt. Sessions are cookie-based using itsdangerous.URLSafeSerializer with a server-side secret key. No OAuth or SSO integration.

Role Model

Two roles: Owner (oawad@alec.ae) and Admin. Owner sees all projects, manages the registry, holds shared Forma credentials, and can access all pending submissions and invite logs. Admins are strictly scoped to their listed projects.

Route Guards

require_user validates the session cookie and rejects unauthenticated requests with a redirect to /login. require_owner additionally checks the authenticated email equals OWNER_EMAIL. Both are applied as FastAPI Depends() arguments.

Public Routes

/login and /portal/platformAccess with its two POST endpoints (/submit and /submit/single) are publicly accessible with no authentication required. The portal is the only intentionally public surface of the system.

Security The SECRET_KEY used for session signing is currently hardcoded in app.py. It should be moved to an Azure App Service environment variable. The users.json file in blob is the only persistence layer for credentials — there is no database.

07
Platforms

Platform Integrations

Revizto

API Endpoints

Two regional servers: api.dubai.revizto.com/v5 and api.ireland.revizto.com/v5. The active region is resolved from active_context.revizto_region in the admin's config. Each admin authenticates with their own access code. Tokens are cached per-region per-admin in blob as revizto_tokens_{region}_{email}.json.

Auth Flow

Access code submitted to POST /oauth/access-code/token to obtain a bearer token (approximately one hour expiry). The token is cached to blob. On expiry, a refresh is attempted automatically using the cached refresh token. License UUID is resolved once via GET /user/licenses and stored in config.

Invite Flow

Two-step operation: (1) add user to the license via POST /license/{uuid}/member/invite, (2) optionally assign a project role via POST /project/{uuid}/role/member/invite. The "Invite to license" and "Invite to project" toggles in the UI control which steps execute. License Admin (role id 4) is blocked across all UI surfaces.

Registry Sync

Project roles fetched via GET /project/{uuid}/role/list and stored under platforms.revizto.roles. License roles (Guest, Collaborator, Content Creator) are hardcoded — they do not require an API call and are always written to the registry on sync regardless of token availability.

Morta

API

api.morta.io/v1. Authenticated with a personal API key set per-admin in Settings. The key is permanent — no token refresh required. There is no owner fallback for Morta. If an admin has not configured their Morta API key, Morta features (search, invite, extraction) are unavailable to them.

Invite Flow

POST /hub/{hub_id}/member/invite. A permission tag can be assigned in the same call by passing tag_reference_id. Tags are synced into the registry from GET /hub/{id}/tags during the registry sync operation and presented as a dropdown in the invite UI.

Search

Members fetched from GET /hub/{hub_id}/members and matched by email. Search is scoped to the hub IDs of the admin's registry projects only. Tags assigned to the matched user are extracted from the member record and returned in the search result.

Extractions

Hub Members (Morta_GET_members), Permission Tags (Morta_GET_Tags), Hub Admins (Morta_GET_Admin). Output written to temp/{email}/ as both CSV and JSON.

Forma / ACC — Autodesk

Auth

Two flows in parallel: 2-legged (client_credentials grant) for account-level operations (hub users, project management), 3-legged (user OAuth) for model-level access requiring user context. The 2L token is cached as forma_tokens.json in blob. Credentials are shared — all admins inherit from the owner config.

Invite Flow

Account-level: POST /hq/v1/accounts/{id}/users/import. Project-level: POST /construction/admin/v1/projects/{id}/users. A single invite call can specify company, role, and product access levels (Docs, Design Collaboration, Model Coordination) simultaneously.

Registry Sync

Companies fetched via GET /hq/v2/accounts/{id}/companies. Project roles fetched via GET /construction/admin/v1/projects/{id}/role-templates. Both stored in the registry under platforms.forma.companies and platforms.forma.roles. Always uses owner credentials.

Extractions

Account Projects, Hub Users, Project Files, Project Models, Model Properties (2L and 3L auth modes), Processed Model Properties. The Forma_MasterScript.py handles token acquisition and stores the result to blob under the COCKPIT_USER namespace.

Scheduler

Scheduler — Shards, Compilers & Run Engine

The scheduler turns one-off extraction runs into recurring automations. Three nested concepts make this work without coupling the data layer to cron. Shards are atomic runnable units (one script + its required context + its output config). Compilers are schedule wrappers that fire one or more shards on cron. Runs are the historical record of every fire — manual or scheduled — with status, files produced, and duration.

Shard — atomic runnable

A shard is everything needed to run one script in one specific way. The script + the resolved context (project ID, model ID where applicable) + the output configuration (formats, file naming, destination) + an optional local-disk pull path for the agent. Once saved, a shard's identity is immutable — to retarget it to a different project, the user deletes and recreates while a different active project is set in the sidebar.

{
  "id":        "sh_AB12CD34",
  "name":      "Wynn weekly Forma model health",
  "platform":  "forma",
  "script":    "Proccesed_Model_Properties",
  "context": {
    "project_id":    "6bf6b4f6-...",
    "model_item_id": "urn:adsk.wipprod:dm.lineage:abc",
    "model_name":    "Wynn 02 Master Model"
  },
  "output": {
    "formats":     ["json", "csv"],
    "prefix":      "wynn_",
    "custom_name": "model_health",
    "naming":      ["append_date", "include_project_name"]
  },
  "destination": {
    "type":        "blob",
    "local_path":  "C:\\\\ALEC\\\\Wynn\\\\Reports"    // optional — agent pull path
  },
  "created_at": 1714780000,
  "created_by": "oawad@alec.ae"
}

Compiler — schedule wrapper

A compiler holds a cron expression (or a daily/weekly/monthly preset) and a list of shard IDs to fire when the cron triggers. One compiler can drive multiple shards — useful for grouped reports that should run as a unit. Compilers are platform-agnostic; the shards inside can mix Revizto, Morta, and Forma scripts.

Run — execution record

A run record captures one execution: shard ID, status (running, success, failed, partial), files produced with their byte sizes, start/end timestamps, the triggering source (manual / scheduler / compiler), and the user attribution. Runs are written twice — once at start with status running, then updated to a terminal status on completion. The Recent Runs UI groups runs hierarchically: top-level entries are one-off manual runs and individual scheduled fires; expandable entries are compiler fires that grouped multiple shards.

The shard builder UI

Source block (Step 1) — Platform → Script → Project (read-only display from active context, snapshotted at save time) → Model picker (only meaningful for L3/L4 scripts; otherwise "— not applicable —"). Output block (Step 2) — Format (JSON/CSV/both), prefix, custom filename, naming flags. Destination block (Step 3) — Blob (default) or Blob + local path (triggers agent delivery).

The model picker is a custom searchable component (the same widget the Extractions page uses). It supports type-to-filter, arrow keys, and enter to select. For Forma projects, the model list is fetched via POST /api/forma/models and filtered to show only models inside any folder named "Shared" (case-insensitive) — most projects' production models live there, and the filter cuts ~1000 raw models down to a manageable list. The cache is shared with the Extractions page; clicking "Fetch Models" there pre-warms the scheduler.

Cron firing engine — APScheduler

The cron firing engine lives in codeShared/Scheduler_Engine.py and uses APScheduler's BackgroundScheduler with a thread pool. On app startup, the engine reads all compilers from blob and registers a CronTrigger for each. When a trigger fires, the engine looks up the compiler's shards and dispatches each through the same runner the Run-Now button uses (codeShared/Scheduler_Runner.py) — so manual and scheduled runs share their entire code path.

Single-instance assumption APScheduler is in-process and single-instance. The Azure App Service B1 plan runs one worker, so this is currently fine. If the cockpit ever scales to multiple workers, the engine would need a distributed lock (Redis or blob lease) to prevent duplicate fires. Not urgent today.

Run-now path

Frontend "Run" button on a shard → POST /api/scheduler/runs/now with the shard ID → server invokes Scheduler_Runner.run_shard() directly (not via the cron engine) → runner builds merged config, spawns subprocess, captures output, writes files to per-run temp dir, uploads to blob, finalises the run record. Same code path as a scheduled fire — the cron engine itself just adds the timing and trigger metadata.

Output file naming

The naming options compose: {prefix}{custom_name|script_name}{_project_name}{_YYYYMMDD}{_HHMMSS}.{format}. overwrite_latest writes a copy without timestamps as well, suitable for "latest export" downstream consumers. Files land in scheduler-exports/ in blob with a 15-day lifecycle policy.

Agent System

Agent System — Tokens & Laptop Pull

Some scheduled extractions need to land on a specific machine — typically a BIM coordinator's laptop or a fileserver — for downstream Revit/Power BI workflows. The cockpit-agent is a small Python script that runs on that machine and polls the cockpit for outputs to download. Authentication uses a per-machine token system separate from admin sessions.

Why an agent and not a webhook

The target machines are often inside ALEC's corporate network behind the firewall, with no public ingress. The cockpit cannot push; the agent must pull. Polling is a deliberately simple model — the agent does not need any open ports or special routing.

Agent tokens

Agent tokens are created in the Agent Tokens page and are scoped to the issuing admin and named for a specific machine ("Omar's laptop"). Each token has an installation date which acts as a gate: when a scheduled run finishes and is destined for a local path, the cockpit only offers the work to agents whose install_date_iso is earlier than the scheduled run's start time. This prevents a freshly issued token from being handed an enormous backlog of historical runs.

{
  "token":            "agt_5f7a3b2c...",
  "label":            "Omar laptop",
  "owner_user":       "oawad@alec.ae",
  "install_date_iso": "2024-04-20T10:00:00Z",
  "created_at":       1714780000,
  "last_seen_at":     1714820000,
  "last_ip":          "10.13.4.22"
}

Wire protocol — claim-based delivery

The agent loops every ~30 seconds polling POST /api/agent/work with its token. The endpoint returns the oldest unclaimed run that has a local-path destination, OR returns { "work": null } if nothing is pending.

1
Agent polls /api/agent/workSends its token. Server validates token + finds the oldest run record with destination.type=blob, a non-empty destination.local_path, status success, and delivery_state=pending.
2
Server claims the run for this tokenAtomic: sets delivery_state=claimed_by:{token_id} with a timestamp. If two agents poll at the same instant, only one wins — the other gets {work:null}. This prevents both Omar's laptop and Sahil's laptop from racing to download the same export.
3
Agent downloads the filesServer returns SAS-signed URLs for each file in the run's output. Agent fetches each, writes them to destination.local_path on the machine, preserving filenames.
4
Agent reports completionPOST /api/agent/done with the run ID and the count of bytes written. Server marks delivery_state=delivered with timestamp. UI shows a green delivery badge in Recent Runs.
5
Stale claim recoveryIf an agent crashes mid-download, the claim is held forever and no other agent ever picks it up. Reaper logic on each poll: if a claim is older than 10 minutes and not delivered, server resets delivery_state=pending so another agent can try.

Phase 1 distribution — .py source

The agent is currently distributed as a Python script (cockpit-agent.py) plus a config.ini.example. Colleagues who want to use it install Python 3, run pip install requests, fill in their token + URL in config.ini, and run the script in a terminal or as a Windows Task Scheduler entry. Phase 2 (PyInstaller .exe build, optional tray icon) is on the backlog but not blocking — the .py path works for the small group using it now.

Compiler-only delivery rule

Manual single-shard runs do not trigger agent delivery, even if the shard has a local_path set. Only runs fired via a compiler get the delivery path. This is intentional: the agent exists for unattended automation, not for one-off downloads. If an admin wants a local copy of a manual run, they download it from the Recent Runs file list in the browser.

Vacation continuity The original motivation for the agent was straightforward: when an admin goes on leave, their scheduled extractions still need to land on the team's shared drive. Issuing a token to a colleague's machine before leaving means scheduled runs continue without intervention — the colleague doesn't need cockpit credentials, just an agent token whose install_date_iso is before the leave date.

Hierarchy

Platform Access Hierarchy

Each platform organises access in a hierarchy of levels. A user must have membership at the top level before they can be assigned to levels below it. The Cockpit manages membership at each level independently — the invite flow lets the admin choose which levels to provision in a single operation.

The dependency is strict — access at a lower level requires membership at the level above it. For Revizto, a user must be on the license before they can be assigned a project role. For Forma, a user must be an account/hub member before they can be given project-level product access. The Cockpit handles all levels in a single invite operation via sequential API calls.

13
Revizto Auth

Revizto Authentication Flow

Revizto uses an access code exchange model. Each admin generates their access code from ws.revizto.com and saves it in Settings. The Cockpit exchanges it for a bearer token and caches the result in blob storage, namespaced per admin and per region. Token refresh is handled automatically on expiry.

Token files are stored per-admin per-region in blob. The key function revizto_get_token_for_region() in app.py handles the full lifecycle — cache check, exchange, refresh, and retry — transparently to the rest of the codebase. Scripts access their token via Revizto_MasterScript.py which reads the same blob key using COCKPIT_USER to namespace correctly.

14
Forma OAuth

Forma / ACC — Two-Legged vs Three-Legged OAuth

Autodesk Platform Services uses two distinct OAuth 2.0 flows depending on the operation. Two-legged (machine-to-machine) is used for all account and project administration — it does not require a user to be present. Three-legged (user-delegated) is used for operations that require a specific user's identity, such as reading model files and element properties from BIM 360/ACC.

Frontend

Frontend Event Model

The frontend is server-rendered HTML with progressive JavaScript enhancement. There is no build step, bundler, or frontend framework. Pages are full page loads from Jinja2 templates. Within a page, dynamic updates are driven by a custom browser event system centred on the sidebar project selector in base.html.

Each child page calls GET /api/context independently on load to restore the active project state. The cockpit:projectChanged event is only dispatched on user-initiated changes within the same page session. This means state is always consistent across page navigations via the server-side blob config, and the event system only handles intra-session dynamic updates.

Performance

In-Memory Cache, TTL & Server Timing

The cockpit runs on a single Azure B1 worker. Every page load that hits blob storage adds 10–30 ms per read. With ~10 reads on a complex page render, that's a quarter-second of latency the user feels as "sluggish." The application avoids this with a process-local read-through cache (_blob_cache) keyed by blob name, with values valid for _BLOB_CACHE_TTL_SEC = 300 seconds.

The cache is intentionally simple — a plain dict, no LRU, no eviction beyond TTL expiry. At the scale of a single tenant on a single worker, the working set fits comfortably in memory; complexity here would buy nothing.

Read-through & invalidate-on-write

Every load_*() function asks _cache_get(key) first; on miss it reads from blob and calls _cache_set(key, value). Every save_*() function writes blob first, then calls _cache_invalidate(key) so the next read fetches the fresh value. This pattern is non-negotiable — forgetting the invalidation in any save path produces a class of bug where users see their own writes for 5 minutes but other tabs see stale data. The Forma 3-legged session save was an example: the original settings_save rebuilt the forma{} dict from scratch, which would have overwritten the OAuth tokens on every Settings save. The fix preserves the 3l_session block explicitly even when other Forma fields change.

Pitfall
Any new mutation path that doesn't go through the existing save_*() helpers will skip cache invalidation and serve stale reads for up to 5 minutes. This is the single most common cause of "why doesn't my change appear?" in development.

Prewarm

On worker boot, _prewarm_cache() reads four high-traffic blobs eagerly: admins.json, projects_registry.json, invite_log.json, portal_requests.json. The first request after a cold start would otherwise pay the blob-read tax for each, leading to a perceptible 100–200 ms first-render delay. Prewarming moves that cost off the request path entirely; the user never sees it.

ServerTimingMiddleware

FastAPI's BaseHTTPMiddleware introduces real overhead — every request creates an extra task, copies bodies through async generators, and adds 5–15 ms to every response on a small instance. The cockpit uses a hand-written pure-ASGI middleware (ServerTimingMiddleware) that wraps the call without that machinery. It records per-request timing via a contextvars.ContextVar and emits a Server-Timing response header. The overhead is a single function call per request — single-digit microseconds.

/api/_diag — production observability

An always-on diagnostic endpoint returns the current cache state, recent timing samples, blob-read latency, and feature flags. It exists for one reason: when production feels slow, you don't want to redeploy with debug code; you want to fetch a JSON object and see exactly where time is going. Sample response:

{
  "_cache_keys_before": ["admins.json", "projects_registry.json", ...],
  "_cache_size": 6,
  "load_users": 0.0,                    // cache hit, sub-millisecond
  "load_registry": 0.0,
  "blob_read_admins_RAW": 9.8,          // cold blob read, milliseconds
  "blob_read_registry_RAW": 8.9,
  "_use_blob": true,
  "_members_cache_size": 1,
  "_members_refreshing": []
}

The discrepancy between cached loaders (0.0 ms) and raw blob reads (8–20 ms) shows the cache's value at a glance. If _cache_size drops back to zero or stays below the prewarm count, the worker has restarted recently. If RAW timings climb above 50 ms, blob storage itself is degraded and the cause is upstream.

Members cache

Distinct from the blob cache: _members_cache holds Morta hub member lists indexed by hub ID, which can be thousands of records and are too large to load on every project-detail render. It refreshes lazily and asynchronously — one stale serve is acceptable; a 3-second blocking refresh on every page load is not. The _members_refreshing set tracks in-flight refreshes so concurrent requests don't fan out into duplicate API calls.

Packages

Bake & Packages — Persistent Snapshots

Extractions write their output into a per-user temp directory that's volatile — it gets cleaned up when the worker restarts, when the user runs another extraction that overwrites the same filename, or when the daily stale-temp sweep runs. For one-shot debugging this is fine, but admins quickly want to share an extraction's output with someone else, view it again next week, or compare two extractions of the same project taken weeks apart. Bake turns a fresh extraction into an immutable, retained, attributable artifact.

Lifecycle

1
RunAdmin clicks Run on an extraction card. The script writes outputs to temp/{safe_email}/*.csv|*.json. The frontend stashes the produced filenames on card.dataset.lastRunFiles.
2
BakeAdmin clicks the (now-active) Bake button. Frontend POSTs to /api/extractions/bake with the file list. Server creates a new pkg_id, copies files to packages/{pkg_id}/, writes metadata to packages_index.json.
3
BrowseThe Packages page lists baked snapshots. Each package shows: platform pill · admin first name · project · timestamp · "expires in N days." Clicking a card expands it inline with file list, Download, and Preview buttons.
4
ExpireAfter 30 days (PACKAGES_RETENTION_DAYS), cleanup_expired_packages() deletes the package directory and removes the index entry on next worker boot.

Visibility rules

RoleSees in /packages
OwnerAll packages, regardless of who baked them or which project
AdminTheir own bakes plus bakes for any project where they're listed in registry[project_id].admins

The check happens server-side via _user_can_see_package(user, pkg, registry); client-side filtering is an optimisation, not a security boundary. Every preview, download, and delete endpoint repeats the check.

Why Forma L1 isn't bakeable

Account Projects, Hub Users, 2-Legged Token Status, and 3-Legged Token Status all describe account-wide Forma state — not project-scoped data. Packaging account data as a per-admin shareable artifact creates more confusion than value: whose hub? when was it captured? does the freshness matter? The bake button is suppressed at the UI level for these scripts, and the backend rejects POSTs targeting them with a clear error.

Storage

Packages live on App Service local disk under packages/{pkg_id}/, not in blob storage. This is a deliberate tradeoff: disk reads stream to the wire faster than blob downloads (the preview endpoint reads small slices on every scroll), and the 30-day retention bounds disk growth. The cost is durability — packages survive worker restarts but not slot swaps or App Service plan migrations. For the current usage profile (single tenant, single environment) this is acceptable; if you ever stage to a separate slot, plan for re-baking.

Preview pipeline

The CSV preview endpoint (/api/packages/{pkg_id}/preview/{filename}) is the most defensively-coded piece in the codebase, because a single malformed request used to crash the worker. The current pipeline is layered:

  1. Cheap stat() first. If the file exceeds PREVIEW_MAX_BYTES (50 MB), return kind: "too_large" with a download URL. The file is never opened — no I/O, no parsing, no risk of OOM.
  2. Streaming CSV scan. For files under the cap, the reader iterates row-by-row. Memory is O(page_size + columns), independent of file size. A 49 MB CSV with 2 million rows uses kilobytes of RAM.
  3. Per-column filters. Query string syntax ?q[colname]=value maps to case-insensitive substring matching. Filters apply server-side over the full file, not just the loaded window. Filtered total drives the frontend's infinite-scroll completion logic.
  4. Row-scan cap. Even with streaming, scanning a 5-million-row CSV ties up the worker for ~15 s. PREVIEW_MAX_ROW_SCAN = 500_000 caps the work per request; past that, the response includes truncated: true and the title bar shows a red "scan truncated at N" badge.

Frontend preview state

Each open preview maintains a state object on the host element (host.__previewState) tracking pagination, active filters, hidden columns, and a loadEpoch counter. On filter input or model switch, loadEpoch increments; in-flight fetches with the old epoch are silently discarded when their responses arrive. This is the standard guard against stale-response races during rapid user input.

Hidden columns are persisted to localStorage under cockpit:pkg:cols:{pkg_id}:{filename}. The key includes pkg_id, so a re-baked package starts with a fresh state — intentional, because the data may have changed. Filter values are not persisted, on the principle that filters are situational queries while column visibility is a configuration preference.

Streaming

Live Streaming Output — Server-Sent Events

An extraction running for 60 seconds in a frozen UI feels like a hang. The cockpit solves this with two extraction endpoints:

/api/extract

Batch endpoint. Runs the script, collects all stdout, returns a single JSON response when done. Used by anything that wants the "script result" as a unit. Backwards-compatible; predates the streaming endpoint.

/api/extract/stream

SSE endpoint. Streams each line of script stdout as it's emitted. Used by the Extractions page terminal so admins see output in real time, like running the script locally in VS Code.

Both endpoints share the same script-resolution, environment-injection, and L4 dependency-check logic. The streaming endpoint adds an async iteration loop and a StreamingResponse wrapper.

Wire format

SSE frames are line-based, with each frame terminated by \n\n:

// per-line stdout, default 'message' event
data: {"type":"line","text":"Found 85 project(s)"}

// keepalive comment — ignored by the client, defeats Azure proxy timeout
:keepalive

// final completion event with status + files
event: done
data: {"status":"success","files":[...]}

The async-readline pattern

Subprocess output handling looks easy until you have a script that goes silent for several minutes (e.g., downloading a 100 MB index from S3). The naïve approach using subprocess.Popen + run_in_executor(proc.stdout.readline) blocks indefinitely on quiet stdout — keepalive code at the bottom of the loop never executes, the SSE stream stays silent, and Azure's ~230 s front-end proxy idle timeout drops the connection. The browser sees "network error" at exactly the 4-minute mark; the script keeps running serverside but its output is invisible.

The fix uses asyncio.create_subprocess_exec with timed reads:

try:
    line_bytes = await asyncio.wait_for(proc.stdout.readline(), timeout=5.0)
except asyncio.TimeoutError:
    if _time.time() - last_heartbeat > 15:
        yield ":keepalive\n\n"
        last_heartbeat = _time.time()
    if proc.returncode is not None: break
    continue

Every 5 seconds the readline is interrupted by the timeout. The keepalive code now runs whether or not the script is producing output. Tested with a script that prints, sleeps 8 s, prints — three keepalives fire during the gap; both real lines are captured intact.

PYTHONUNBUFFERED=1

Python's stdout is line-buffered when connected to a terminal but block-buffered when piped to a subprocess parent. Without intervention, a script's print() calls would accumulate in Python's internal buffer and emit in 4 KB chunks — defeating the live-streaming illusion before it even reached SSE. The cockpit injects PYTHONUNBUFFERED=1 into the subprocess environment, which tells Python to flush stdout after every write. The companion -u flag on the Python invocation is belt-and-suspenders.

Frontend consumption

The browser uses fetch().body.getReader() rather than EventSource. Two reasons: EventSource only supports GET (the cockpit POSTs the script name + project context), and fetch handles auth cookies and JSON request bodies without ceremony. The reader yields chunks; a small parser splits on \n\n and routes frames by event type. A state.loadEpoch counter discards any frame whose enclosing run was cancelled by a newer one — same pattern as the package preview filters.

Connection cancellation

If the user navigates away mid-run, the FastAPI generator catches asyncio.CancelledError and calls proc.kill() to terminate the subprocess. Without this, the script would continue running, hold its temp dir locks, and waste API quota. The kill is best-effort; an already-exited process raises an exception that we swallow.

L4 Reports

L4 Reporting Layer & Dependency Tracking

Layer 4 scripts (Reporting) consume the output of an L3 extraction and produce a derived report. Forma's Model Health Report is the first such script: it reads the model properties extracted by Forma_GET_Model_Properties and emits aggregated health metrics. The risk is silent staleness — if the user runs Properties for Model A, switches to Model B, and clicks Health Report, the report would run against Model A's data while presenting itself as Model B's. The output is plausible-looking, signed with the wrong model, harder to catch than an outright failure.

The dependency mechanism is generic

L4 dependencies are declared once, in a single map:

L4_DEPENDENCIES = {
    "Proccesed_Model_Properties": {
        "platform":           "forma",
        "requires":           "Forma_GET_Model_Properties",
        "context_path":       "forma.model_item_id",
        "context_label_path": "forma.model_name",
        "human_prereq":       "Model Properties",
        "human_thing":        "model",
    },
    // Future entries land here. UI gating, run-time check, and stamping
    // all flow from this single declaration.
}

context_path is a dotted path into the user's config that yields the value being processed (the active model URN). context_label_path resolves to a human-readable label for use in error messages. Adding a new L4 report — say, a Revizto clash-summary that depends on Object Tree extraction — is one entry plus the script itself.

Two-phase enforcement

The check fires twice on every L4 invocation:

A
UI gatingThe Run button on each L4 card is faded/disabled until /api/l4/status?script=... returns ready: true. Status check fires on page load, on cockpit:modelChanged events from the model selector, and on every successful Run completion (which may have just satisfied the dependency).
B
Server-side pre-flightIf the UI gate is bypassed (DevTools, direct API call, race condition), /api/extract and /api/extract/stream independently call _check_l4_dependency before spawning the subprocess. Mismatch returns HTTP 409 with a clear error message; subprocess is never started.

Stamping success

When an L3 prerequisite finishes successfully, _stamp_l3_run(user, script_name, files) writes a record to the user's config:

{
  "forma": {
    "model_item_id": "urn:adsk.wipprod:dm.lineage:abc",
    "model_name":    "Building A",
    "last_runs": {
      "Forma_GET_Model_Properties": {
        "context_path":  "forma.model_item_id",
        "context_value": "urn:adsk.wipprod:dm.lineage:abc",
        "context_label": "Building A",
        "ran_at":        1730000000,
        "files":         ["forma_model_properties.csv"]
      }
    }
  }
}

Only scripts named in some L4_DEPENDENCIES[*].requires are stamped — the set _L3_TRACKED_PREREQS is computed at module load. Other scripts run normally without leaving a record, keeping the config small.

Cache headers matter

The status endpoint returns Cache-Control: no-store, and the frontend fetch passes cache: 'no-store'. Both layers, because either alone misses some browser quirk. Without these, the browser would happily serve a cached pre-switch response when the user changes models — the status text would lag behind the dropdown until a hard refresh. This bug existed for one round before being caught; the lesson is that any GET returning rapidly-changing state needs explicit cache control even if the data itself is correct.

Per-admin scope

The last_runs record lives in each admin's individual config blob. The owner running Properties doesn't satisfy the dependency for other admins on the same project — each admin must run the prerequisite themselves. This is correct: Forma's permissions are user-scoped, and the report runs as the calling admin's identity (via the per-admin 3-legged token). Coupling the dependency check to the admin running it ensures the data and identity stay aligned.

Deploy

Deploy Pipeline & Operational Discipline

The cockpit deploys as a single zip pushed directly to App Service via the Azure CLI. There is no CI/CD, no build step, no staging slot. This is by design — the system is small enough that ceremony adds friction without buying safety, and the entire deploy fits in three commands.

The deploy command

git archive --format=zip --output=deploy.zip HEAD
az webapp deploy --resource-group digitalcockpit-rg \
                 --name digitalcockpit-alec \
                 --src-path deploy.zip --type zip

git archive exports a clean snapshot of HEAD — only tracked files. If your working tree contains uncommitted changes, they're not in the deploy. This is a feature: it's impossible to ship local edits you forgot about. It's also a foot-gun: it's possible to commit a change but forget to deploy, leaving the live site behind your repo.

az webapp deploy uploads the zip to the kudu deployment endpoint, where it's extracted in place. Worker processes restart automatically. Total deploy time is typically 30–60 seconds; the first request after deploy hits a cold cache and prewarm runs.

Cross-file dependencies — ship together

A frontend change that calls a new API endpoint and the backend code defining that endpoint must deploy in the same zip. Splitting them produces a window where either the UI shows a feature that 404s, or the backend serves an endpoint nothing calls. The cockpit has been bitten by this several times — most recently when the SSE frontend shipped before its /api/extract/stream endpoint, producing repeated "Stream failed: HTTP 404" errors on every Run.

Rule
If a change touches both app.py (or any backend file) and any template/CSS/JS, deploy them together in one zip. README files for these bundles should explicitly list cross-file dependencies under a "ship together" heading.

The .gitignore foot-gun

On Windows, a file saved as gitignore (no leading dot) is not recognised as a git ignore file. Git silently treats it as a regular tracked file and ignores nothing. The cockpit's repository was in this state for an extended period, allowing several runtime-secret JSONs to be committed before the issue was noticed.

The fix is twofold: rename the file (git mv gitignore .gitignore) and audit history for any committed secrets via git ls-files | findstr against known-secret patterns. Anything found in history is rotated immediately — old credentials remain in past commits forever even after deletion from HEAD, which is fine once they've been invalidated upstream.

Credential rotation playbook

Every credential the cockpit holds is rotatable without code changes:

Saving in the Settings UI writes directly to blob storage (the production source of truth). No deploy required for credential changes. Local files are stale moments after rotation but get refreshed next time the worker reads from blob.

Working with stale local snapshots

Multi-round development has a recurring pattern: an AI assistant or human developer holds a snapshot of files from session N, the user makes edits in session N+1 that aren't reflected in the snapshot, and a careless edit overwrites the user's work. The defensive habit is to ask before editing any file that's been around for more than one session, especially HTML and Python that change frequently. Several near-misses during the cockpit's development were caught only by this question.

Limits

Resource Constraints & Hard Limits

The cockpit runs on Azure App Service B1 — the smallest tier that supports always-on with a meaningful CPU allocation. Knowing the constraints turns "the site went down" into "here's exactly what hit a limit."

Compute & memory

RAM1.75 GBLoading large CSVs into memory; many concurrent script subprocesses

The 230-second proxy timeout

Azure App Service's front-end load balancer drops idle connections at roughly 230 seconds. "Idle" means no bytes flowing in either direction. For SSE this is fatal during long quiet phases — a script downloading a 100 MB index from S3 produces no stdout for minutes, the SSE stream stays silent, the proxy kills the connection. The fix (heartbeat comments every 15 s) is documented in the Streaming section.

Memory hardening

Two patterns dominate OOM defense:

Stream, don't materialise

Anywhere the size of input is unbounded — CSV preview, package listing, member lists — iterate the source and retain only the working window. list(reader) is a red flag in any code path that touches user files. The 126 MB CSV that crashed the worker did so because the preview endpoint did exactly that.

Cap before opening

For inputs where streaming still risks a slow blow-up (a 49 MB CSV of 5 million short rows takes 15 seconds to scan even streamed), cap with a cheap stat() before any I/O on contents. The preview cap (50 MB byte limit, 500 k row scan limit) applies before the file is ever opened.

Growth rates worth watching

Three internal data structures grow over time and don't currently auto-archive. None are urgent at current usage but each becomes a problem at some scale:

  • invite_log.json — appended on every invite. Grows linearly with usage. Loaded fully into memory on every Manage page render. At ~10,000 entries (~1 invite/day for 27 years), Manage page load times become noticeable. Mitigation when needed: rolling-window archival to invite_log_archive_{year}.json with the live file holding only the last 90 days.
  • portal_requests.json — same shape, same growth rate, same eventual mitigation.
  • _blob_cache — per-user config keys are added on first read and never evicted. At 100 admins each visited once, ~100 keys × ~5 KB = 500 KB. Survivable. At 10,000 unique users, 50 MB and growing — would need eviction. Currently unbounded by intent because the user count is bounded by the @alec.ae domain restriction.
  • packages/ directory — bounded by the 30-day retention sweep, but a single 126 MB Forma model bake from each of 10 admins per day is 1.2 GB/day. Disk could fill before retention catches up. Worth monitoring; not yet at risk.

What scaling up looks like

The current architecture comfortably supports the present scale. Hypothetical paths if growth demands it: B1 → S1 (3.5 GB RAM, more headroom for memory-bound previews); single worker → multi-worker (requires moving in-memory caches to a shared layer like Redis); local-disk packages → blob-storage packages (loses preview latency but gains durability across slot swaps and blob-managed retention). None of these are needed today; all are tractable when they are.
