01
Overview

System Overview

The Digital Construction Cockpit is a single-tenant FastAPI web application hosted on Azure App Service that consolidates BIM data extraction, project administration, and access management for ALEC's construction technology stack. It interacts with three external platforms: Autodesk Forma / ACC for design and model data, Revizto for clash detection and issue tracking, and Morta for tabular project data.

Authentication is restricted to @alec.ae email addresses backed by per-admin records in blob storage. The system uses Azure Communication Services for transactional email — invitations, password resets, and platform onboarding flows. There are no consumer-facing surfaces; every authenticated user is an admin with full read/write access to the cockpit's shared registry of projects, members, and automations.

Architecturally, the cockpit is a thin orchestration layer over standalone Python extraction scripts. The web application receives requests from the browser, merges per-admin credentials into a temporary config file, and launches the appropriate script as a managed subprocess with its environment populated by environment variables. The script writes output to a per-admin temp directory; the cockpit streams stdout to the browser via Server-Sent Events and serves the resulting files via signed download links.

System characteristics

  • Single-tenant. One App Service, one storage account, one ALEC-only login pool. No multi-tenant isolation needed.
  • Stateless workers, stateful storage. The FastAPI process keeps an in-memory TTL cache, but the source of truth for every persistent decision lives in blob.
  • Subprocess-driven extraction. Long-running platform calls (Forma L3 model property dumps in particular) run in a separate Python process so they can stream output without blocking the event loop and so memory is reclaimed on script exit.
  • Per-admin isolation at runtime, shared state at registry level. Two admins can run extractions simultaneously without collision because temp files and config files are scoped by email; but the project registry and admin records are shared.

Lifecycle rules on storage

The cockpitdatastorage account has a single lifecycle rule named auto-delete-exports-after-15-days. It is scoped to three prefixes — forma-exports/, revizto-exports/, morta-exports/ — and deletes blobs whose last-modified date exceeds 15 days. The cockpit-data container is explicitly NOT in scope: it holds permanent runtime state (admin records, registry, token caches, portal submissions) that must not auto-delete.

Lifecycle scope is critical
If the lifecycle rule is ever modified to "all blobs in the storage account," the cockpit will silently lose admin records, project registry, and portal submissions on the 16th day after a write. Always verify the prefix filter is intact before touching this rule.
03
Storage

Blob Storage Layout

Persistent state is partitioned into four containers, each with its own access pattern, retention policy, and code path that touches it.

cockpit-data

Purpose: All runtime state. Admin records, project registry, per-admin configs, invite logs, portal submissions, token caches, scheduler state.

Retention: Permanent. NOT covered by the lifecycle rule.

Accessed via: app.py's internal blob_read() / blob_write() helpers. Cached in-memory with a 5-minute TTL.

forma-exports

Purpose: Output files from scheduled Forma extractions when destination is blob. Path convention: YYYY-MM-DD/<shard_id>/<model>.json.

Retention: 15 days after last modified.

Accessed via: codeShared/Blob_Client.py — a module deliberately separate from app.py's blob client. SAS URLs generated on demand for download.

revizto-exports

Purpose: Output files from scheduled Revizto extractions. Path convention same as Forma.

Retention: 15 days.

Accessed via: Blob_Client.py.

morta-exports

Purpose: Output files from scheduled Morta extractions. Eventually also the destination for Morta upsert/append/replace ingestion.

Retention: 15 days.

Accessed via: Blob_Client.py.

Two blob clients, two responsibilities

The codebase has two distinct blob client layers. They share the same connection string but operate on different containers and have different concerns:

app.py — internal client

Touches only cockpit-data. Provides blob_read(name), blob_write(name, data), and blob_delete(name). Not exported. Coupled to the in-memory TTL cache: every load_* function uses _cache_get, every save_* calls _cache_invalidate.

codeShared/Blob_Client.py — exports client

Touches only forma-exports / revizto-exports / morta-exports. Hard-rejects writes to cockpit-data with ValueError. Provides upload_blob, upload_file, generate_download_url, list_blobs, delete_blob. No caching. Built for the scheduler.

Why split?
The internal client is bound up with cache invalidation logic that doesn't apply to export blobs. Keeping them separate means the scheduler can write to its containers without accidentally invalidating cached admin/registry state, and the runtime-state container can never be accidentally touched by the scheduler code path.

Registry

Project Registry — Backbone of the Access Model

projects_registry.json is the single source of truth for which admin sees what. It maps a stable project key to all platform identifiers, assigned admins, and live-synced metadata. Every scoped operation — what shows in the sidebar, what appears in user search, which tags and roles populate invite dropdowns — is derived from this file.

Registry sync (POST /api/registry/project/{key}/sync) fetches live data from each platform and writes it back. If the syncing admin has not configured their Morta API key or Forma credentials, the system falls back to the owner's credentials — except for Morta, where keys are strictly personal and no fallback is applied.

What depends on the registry

Access rule
Only the owner (OWNER_EMAIL) can create, update, or delete registry entries. Write routes use require_owner. GET /api/registry returns a user-scoped subset — non-owners only receive projects where their email appears in admins[].
04
Auth

Authentication & Access Control

Authentication is single-tenant: only @alec.ae emails can sign in or be invited. The owner email (OWNER_EMAIL environment variable) carries elevated rights for cross-cutting concerns like rotating shared Forma credentials and granting admin access to other emails. Every other authenticated user is a regular admin with full access to the shared registry.

Session model

  • Sessions are signed cookies issued by itsdangerous's URLSafeSerializer. The cookie payload is the raw email; the signature is checked on every request.
  • The signing key is SESSION_SECRET (env var). Rotating it invalidates every active session at once, which is fine for incident response — admins simply log in again.
  • There is no expiry on the session signature itself; sessions persist until the user logs out or the secret rotates.

The require_user dependency

FastAPI's dependency injection is the gate. Routes that need authentication declare user: str = Depends(require_user). require_user reads the session cookie via get_current_user; on missing or invalid signature, it raises a 303 redirect to /login. There is no separate "logged-in user" vs "admin user" check — every authenticated identity is an admin.

Owner-only operations

A small set of operations require require_owner instead. These include:

  • Editing the shared Forma client credentials (impacts every other admin)
  • Granting initial admin status to a new email
  • Sending test emails via /api/test-email
  • Hard-deleting another admin's records

Password storage

Passwords are stored as raw SHA-256 hashes in admins.json. There is no salt and no key-derivation function (PBKDF2/bcrypt). This is a known weakness — adequate for an internal tool with rate-limited login on a single tenant, inadequate for any public-facing surface.

Roadmap item
If the cockpit ever expands beyond ALEC-internal use, password hashing must be upgraded to bcrypt or Argon2id with per-user salts. The current scheme is a calculated tradeoff for a small internal team, not a permanent choice.

Config

Per-Admin Config & Shared Credential Inheritance

Each admin has a personal config blob, config_{safe_email}.json. It holds their Revizto credentials per region, their Morta API key, and (for the owner only) the shared Forma client credentials that all other admins inherit when their own credentials are absent.

Before any extraction script runs, app.py's build_script_config() function merges three sources in order:

1
Load the triggering admin's personal configFrom config_{safe_email}.json in blob. This contains their Revizto access codes for both regions, their Morta API key, and any Forma credentials they've saved personally.
2
Merge in the owner's shared Forma block if absentIf the admin's own forma.client_id or forma.client_secret is empty, fall back to the owner's stored values. This way, ALEC's Forma application registration is set once and works for everyone.
3
Inject the active contextThe script-specific context — project ID, model item ID, model name — is added under the active_context key. Different scripts read different fields from this section.
4
Write the merged config to a temp filetemp/{email}/_cockpit_config.json. Files prefixed with _ are excluded from the user-facing download list, so this internal scaffolding doesn't appear as a downloadable export.
5
Pass the path via COCKPIT_CONFIG env varThe subprocess inherits the env var. Each platform's *_Config.py module reads os.environ["COCKPIT_CONFIG"], opens the file, and pulls out its slice of the merged config. Scripts never read from blob directly; they only read this temp file.

06
Cache

In-Memory Cache, TTL & Prewarm

Without caching, every page load would make 3–5 blob round-trips just to render the navbar (the loaders for users, registry, config, and invite_log are called from multiple spots in the same request). To avoid that, app.py wraps every load_* function in a tiny TTL cache.

Read-through, invalidate-on-write

  • TTL: 5 minutes per cache key. Tuned after profiling showed shorter values (5 seconds initially) discarded entries before subsequent requests arrived.
  • On read: _cache_get(key) returns the value if non-expired; otherwise the loader fetches from blob and calls _cache_set.
  • On write: Every save_* function calls _cache_invalidate(key) immediately after the blob write, so reads on the next request always see the new value.
  • Out-of-band edits: If someone edits a JSON file directly in the Azure portal (rare but possible), changes become visible within 5 minutes. There is no push-based invalidation across instances — but the App Service runs single-instance so this isn't a concern.

Prewarm at startup

At import time, app.py calls _prewarm_cache() which fires off the heavy loaders in parallel via a small ThreadPoolExecutor. By the time the first request arrives, the cache is populated and the response feels instant. If prewarm fails (blob unavailable, transient network), it logs and continues — the loaders fall back to direct blob reads on first request.

Server-Timing observability

A small middleware called ServerTimingMiddleware measures the time spent in each major phase of a request and emits the data as a Server-Timing response header. Browsers display this in DevTools under the Network panel. Phases tracked: load_users, load_registry, load_config, load_invite_log, plus the actual route handler runtime.

/api/_diag — production observability endpoint

Owner-only diagnostic endpoint. Returns a single JSON document with cache hit/miss counters, environment-variable presence checks (without leaking values), blob round-trip timing samples, and a summary of which loaders the prewarm step succeeded or failed on. This is how operational health is checked without standing up App Insights or another full observability stack.

{
  "env": {
    "AZURE_STORAGE_CONNECTION_STRING": true,           // presence only, never value
      "AZURE_COMMUNICATION_CONNECTION_STRING": true,
    "OWNER_EMAIL": true
  },
  "cache": {
    "hits": 1247, "misses": 52, "evictions": 12,
    "keys": ["admins.json", "projects_registry.json", ...]
  },
  "blob": { "sample_read_ms": 12, "sample_write_ms": 38 },
  "prewarm": { "ok": ["users", "registry", "invite_log"], "failed": [] }
}

Members cache (cross-platform)

A separate cache for cross-platform member queries. When the registry lists "members of project X," the data comes from each platform's API (Forma project members, Revizto project users, Morta hub members). Querying these three on every page load would be slow; a 60-second cache keyed by project + platform reduces redundant calls during typical browsing.

app.py is a single-file FastAPI application of approximately 6,400 lines. Frontend architecture

Templates extend a single base.html that defines the navbar, sidebar, theme variables, and a smartFetch utility. smartFetch reads from localStorage for an instant render, then revalidates against the server in the background and updates the UI on fresh data — a pattern stolen from stale-while-revalidate cache semantics.

The frontend ships zero build tooling. No webpack, no TypeScript compilation. JavaScript is written inline in template files or in static/js/*.js as plain ES2020. Tailwind-style utility classes are NOT used — styling is via the CSS variables defined in base.html and component-scoped classes in the page templates themselves.

Revizto Auth

Revizto Authentication Flow

Revizto's auth model is per-user per-region. Each ALEC admin who needs Revizto access generates a personal access code from the Revizto web UI and pastes it into the cockpit's Settings page. The cockpit exchanges the code for a token pair and from then on handles refresh transparently.

1
Admin pastes access code into SettingsUI sends to POST /api/revizto/exchange with the code and region. The cockpit calls Revizto's /oauth2/token endpoint with grant type authorization_code.
2
Token pair returned and storedAccess token (~1h life) and refresh token (~30d life) written to revizto_tokens_{region}_{safe_email}.json. The blob also stores obtained_at and expires_at Unix timestamps for later staleness checks.
3
Subsequent requests check freshnessrevizto_get_token_for_region(email, region) checks expires_at; if within a 30-second safety margin, it calls the refresh endpoint and writes the new token pair back. The script layer never sees this — it just gets a valid bearer.
4
Refresh token expiryIf the refresh token itself is expired or revoked, the refresh endpoint returns a 401. The cockpit surfaces this on Settings as "Re-authentication required" — the admin pastes a new access code.

Token namespace via COCKPIT_USER

When a script is launched as a subprocess, the env var COCKPIT_USER is set to the triggering admin's email. Revizto_MasterScript.py reads this value to compute the same blob key the web layer uses, so the script reads the same token cache the cockpit just refreshed. This is the namespacing mechanism that lets concurrent admins run scripts without colliding.

Forma OAuth

Forma / ACC — Two-Legged vs Three-Legged OAuth

Autodesk Forma sits on the Autodesk Platform Services (APS) auth stack. APS supports two flavors of OAuth, and the cockpit uses both for different purposes:

2-legged (client credentials)

Application authenticates as itself using client_id + client_secret. No user is involved. Useful for license-level reads and for any operation that doesn't need to act as a specific Autodesk user.

Storage: forma_tokens.json, single shared entry.

Scopes: data:read account:read

Refresh model: Token has ~1h life. Cockpit re-acquires from /authentication/v2/token on demand. No refresh token — credentials are re-presented each time.

3-legged (authorization code)

User-level OAuth. The admin clicks "Connect Forma" in Settings and is redirected to Autodesk's consent screen. After consent, the cockpit receives an auth code, exchanges it for an access + refresh token pair scoped to that admin.

Storage: forma_tokens_3l.json, keyed by safe email.

Scopes: data:read data:write account:read

Refresh model: Standard refresh-token flow. ~14-day refresh lifetime; cockpit auto-refreshes.

When each is used

  • 2-legged: Listing account-level projects, basic project metadata, license members. The bulk of Forma extraction scripts.
  • 3-legged: ACC-specific operations where Autodesk requires a user identity for audit purposes — granting ACC project access, modifying project users, certain hub operations.

The shared-credentials model

The owner's config.forma.client_id and client_secret are the application credentials. Other admins inherit these via the merge step described in section 05. They don't see the raw values — when an admin opens Settings, the Forma fields show as masked. Only the owner can edit them.

Hierarchy

Platform Access Hierarchy

Each platform organises access in a hierarchy of levels. A user must have membership at the top level before they can be assigned to levels below it. The cockpit manages membership at each level independently — the invite flow lets the admin choose which levels to provision in a single operation.

The dependency is strict — access at a lower level requires membership at the level above it. For Revizto, a user must be on the license before they can be assigned a project role. For Forma, a user must be an account/hub member before they can be given project-level product access. The cockpit handles all levels in a single invite operation via sequential API calls.

Scripts

Script Layer

All data extraction logic lives in standalone Python scripts. They can run directly from a terminal in local development, or be triggered by the web app as managed subprocesses in production. Each script imports its platform config module (*_Config.py) which reads the merged config from COCKPIT_CONFIG and writes output to COCKPIT_EXPORTS_DIR. Internal files starting with _ are excluded from the download list presented to the user.

The naming convention

Each platform's scripts follow the same shape:

  • {Platform}_Config.py — single-file config loader. Reads COCKPIT_CONFIG, exposes constants like BASE_URL, API_KEY, etc. Other scripts import from here.
  • {Platform}_MasterScript.py — handles token acquisition, refresh, and blob persistence of tokens. Other scripts call get_access_token() from here.
  • {Platform}_GET_*.py — extraction scripts. Each one is self-contained, reads its slice of config, calls APIs, writes output.
  • Proccesed_*.py — derived processing scripts that read another script's output and produce a refined report (Forma L4, primarily).
Note on the typo
Proccesed_Model_Properties.py has a real misspelling — "Proccesed" should be "Processed". It was named that way in early prototypes and is now widely referenced; renaming would break dependency stamps and existing baked packages, so it stays.

Tiers

Extraction Tiers — L1 through L4

The cockpit organizes every platform's data into a four-tier hierarchy. The tiers are a generic dependency model: each one operates at a wider or narrower scope than the one above it, and tiers further down depend on the artifacts produced by tiers above. The model is identical across Forma, Revizto, and Morta — what differs is which entity each tier addresses on each platform.

The generic tier model

L1 — Tenant scope

The widest scope. Operates on the platform-level tenant: the account, the license, the hub. Lists what exists across the entire deployment. Typically global per-platform, not project-scoped.

Output volume: small (KB–MB). Volatile — projects, members, licenses come and go.

L2 — Project scope

Narrows to one project. Lists what's inside it: models, members, issues, tables, etc. Usually requires only an active project context — doesn't strictly need L1 to have run, since the project ID can come from anywhere.

Output volume: small to medium (MB).

L3 — Resource scope

Narrows further to one specific resource within a project — a single model, a single issue tracker, a single member set. Pulls the full element-level or row-level data. This is where the heavy lifting happens.

Output volume: large (MB–GB). Wynn-scale Forma models produce ~1 GB of JSON.

L4 — Derived report

A processing tier rather than an extraction tier. Reads L3 output (or L2 in some cases) and produces summary reports, aggregates, health metrics. Doesn't talk to the platform API at all — pure transformation.

Output volume: small (KB). The whole point is to compress L3 down to something a human can scan.

Why L2 and L3 sometimes collapse
For Revizto, the /issues endpoint already returns the full per-issue payload in one call — fetching the project's issue list and fetching each issue's details aren't separate operations. So Revizto's L3 is folded into its L2 script. The tier model is descriptive, not prescriptive — what the platform API gives you in one call stays in one call.

Dependency stamping

The cockpit enforces tier dependencies by stamping success markers in the output directory. When a script finishes successfully, the cockpit writes _done.{script_id} to COCKPIT_EXPORTS_DIR. When a child-tier script is requested, the cockpit checks for the parent's marker; if absent, POST /api/extract/start returns 412 Precondition Failed with a hint to run the prerequisite first.

This is deliberately blunt. The alternative — auto-running the parent when a child is requested — would hide cost from the admin (a "quick" L4 click would secretly trigger a 20-minute L3 run on a large model). Forcing the explicit run keeps the cost visible.

Cross-tier reuse via Bake

Once L3 has run for a model, an admin can Bake the result so other admins on the same project don't have to re-run it. When admin B opens the same project, the cockpit detects the baked package and offers L4 directly — admin B never spent the 20 minutes that admin A did. The dependency check still passes because L3's marker is implicit in the baked package's presence.

The L4_DEPENDENCIES map — single declaration drives everything

L4 dependencies are declared once, in a single Python dict. UI gating, run-time check, and stamping all flow from this declaration:

L4_DEPENDENCIES = {
    "Proccesed_Model_Properties": {
        "platform":           "forma",
        "requires":           "Forma_GET_Model_Properties",
        "context_path":       "forma.model_item_id",
        "context_label_path": "forma.model_name",
        "human_prereq":       "Model Properties",
        "human_thing":        "model",
    },
    // Future entries land here. Adding a Revizto clash-summary that
    // depends on Object Tree extraction is one entry plus the script.
}

context_path is a dotted path into the user's config that yields the value being processed (e.g. the active model URN). context_label_path resolves to a human-readable label for use in error messages. Adding a new L4 report to a different platform is a single-entry addition — no new mechanism, just data.

Two-phase dependency enforcement

The dependency check fires twice on every L4 invocation. The redundancy is intentional — defence in depth against UI bypass and race conditions:

A
UI gating (browser side)The Run button on each L4 card is faded and disabled until /api/l4/status?script=... returns ready: true. Status check fires on page load, on cockpit:modelChanged events from the model selector, and on every successful Run completion (which may have just satisfied the dependency).
B
Server-side pre-flight (independent re-check)If the UI gate is bypassed (DevTools, direct API call, race), /api/extract and /api/extract/stream both call _check_l4_dependency before spawning the subprocess. Mismatch returns HTTP 409 with a clear error; subprocess is never started. The risk this prevents is silent staleness — running the L4 against the wrong model's data.

The stamp record schema

When an L3 prerequisite finishes successfully, _stamp_l3_run(user, script_name, files) writes a record to the user's config:

{
  "forma": {
    "model_item_id": "urn:adsk.wipprod:dm.lineage:abc",
    "model_name":    "Building A",
    "last_runs": {
      "Forma_GET_Model_Properties": {
        "context_path":  "forma.model_item_id",
        "context_value": "urn:adsk.wipprod:dm.lineage:abc",
        "context_label": "Building A",
        "ran_at":        1730000000,
        "files":         ["Building A.json", "Building A_RawCounts.json"]
      }
    }
  }
}

Only scripts named in some L4_DEPENDENCIES[*].requires are stamped — the set _L3_TRACKED_PREREQS is computed at module load. Other scripts run normally without leaving a record, keeping the per-admin config small.

Cache-Control headers matter

The L4 status endpoint returns Cache-Control: no-store, and the frontend fetch passes cache: 'no-store'. Both layers, because either alone misses some browser quirk. Without these, the browser would happily serve a cached pre-switch response when the user changes models — the status text would lag behind the dropdown until a hard refresh. This bug existed for one round before being caught; the lesson is that any GET returning rapidly-changing state needs explicit cache control even if the data itself is correct.

Per-admin scope of the dependency check

The last_runs record lives in each admin's individual config blob. If admin A runs Properties for a model, admin B running the L4 report on the same model still has to run Properties themselves first. This is correct: Forma's permissions are user-scoped, and the report runs as the calling admin's identity (via the per-admin 3-legged token). Coupling the dependency check to the admin running it ensures the data and identity stay aligned. Bake is the explicit escape hatch when admins genuinely want to share the L3 result.

Forma-specific tier details

Forma's L3 deserves a closer look because it's by far the heaviest extraction in the system and has shaped much of the cockpit's memory and streaming architecture.

The KEPT_CATEGORIES filter

Forma returns approximately 200 distinct Revit categories per modern model — many of which are not physically meaningful (annotation symbols, view-specific data, scope boxes). The cockpit's L3 implementation maintains a KEPT_CATEGORIES set of the ~60 categories that represent actual physical building elements, plus Revit Project Information, Revit Document, Revit Project Base Point, Revit Survey Point, Revit Phases, and Revit Family Type for metadata extraction.

For categories in this set, full element rows are written to the per-category temp file. For categories outside the set, only counts are recorded. Both are reflected in the final RawCounts.json, but only kept categories appear in the grouped {ModelName}.json.

L4 Aggregate — three-level hierarchy

The aggregate file shape is intentionally not "categories with families with types" using wrapper keys. Instead, the hierarchy is encoded directly in nested JSON structure where each value is itself the breakdown:

{
  "Revit Structural Columns": {
    "count": 48,
    "Direct Shape": {
      "count": 35,
      "ROD32": { "count": 20 },
      "ROD25": { "count": 15 }
    },
    "Generic Column": {
      "count": 13,
      "10x10": { "count": 8 },
      "12x12": { "count": 5 }
    }
  }
}

The fallback chain for type name is: Type Name → _RFT → name → "<no type>". For family it's _RFN → "<no family>". This keeps the report robust against partial data.

Memory profile

Forma L3 and L4 are designed to run within the App Service B1 memory budget (1.75 GB total, ~1.4 GB practically usable). L3 streams element rows to per-category temp files as it receives them; only one row plus a small file-descriptor map is in memory at any given time. L4 uses a line-based streaming reader that detects category headers ("<Category>": [) without parsing the full JSON. Peak memory during L4 stitching is ~200–400 MB for a Wynn-scale model.

The other platforms' tiers don't have this problem because their data is orders of magnitude smaller — Revizto and Morta L1/L2 outputs are typically a few MB, well within naive in-memory handling.

Extraction

Extraction Run — Subprocess Lifecycle

Every manual extraction follows the same lifecycle. The cockpit tracks the run via a stream ID returned at start, which the browser uses to subscribe to SSE updates and to cancel mid-run if needed.

1
Browser POSTs to /api/extract/startBody: script_id, context (project_id, model_item_id, model_name, region — varies by script). Cockpit validates the script exists, the admin has the required credentials, and any dependency stamps are present.
2
build_script_config() runsMerges admin config with owner Forma fallback, injects active context, writes to temp/{email}/_cockpit_config.json.
3
Subprocess spawnedPython subprocess launched with COCKPIT_CONFIG, COCKPIT_EXPORTS_DIR, COCKPIT_USER, and PYTHONUNBUFFERED=1. Stdout and stderr are both piped to async readers.
4
Cockpit returns stream IDThe HTTP request returns immediately with { "stream_id": "..." }. The subprocess continues running in the background.
5
Browser subscribes via GET /api/extract/stream/{id}SSE channel. Each line of subprocess stdout becomes a data: event. The browser appends to a live log panel.
6
Script writes outputsFiles appear in temp/{email}/. As soon as the subprocess exits, the cockpit closes the SSE channel and stamps a success marker (_done.{script_id}) which downstream dependency checks reference.
7
Browser fetches /api/exportsLists files in the temp dir, filtering out _-prefixed internal scaffolding. Each file gets a download link via /api/exports/{filename}.

Cancellation

The browser can cancel a running extraction by closing the SSE connection. The cockpit detects the disconnect and sends SIGTERM to the subprocess. If the subprocess doesn't exit within 5 seconds, SIGKILL follows. Files written before cancellation remain in the temp dir; the success marker is NOT stamped, so downstream dependency checks correctly treat the run as failed.

Concurrency

Two admins running extractions simultaneously are fully isolated — different temp dirs, different config files, different token cache namespaces. The same admin running two extractions in parallel is also OK if the scripts target different output filenames; if they target the same file (e.g. two L3 runs on the same model), the second one will overwrite the first's outputs without warning.

Streaming

Live Streaming Output — Server-Sent Events

Long-running extractions stream their stdout to the browser in real time so admins can see progress and catch issues without waiting for the script to complete. The mechanism is server-sent events (SSE) — a one-way channel from server to browser over a long-lived HTTP response.

Wire format

Each line of subprocess stdout is wrapped as a single SSE event:

data: {"type": "log", "line": "Fetching model 1 of 23..."}

data: {"type": "log", "line": "Wrote temp/file_1.json (1.4 MB)"}

event: done
data: {"status": "success", "duration_sec": 47.3}

The async-readline pattern

FastAPI's async event loop and Python's blocking subprocess.stdout.readline() don't mix. The cockpit uses an async wrapper that reads from the subprocess stdout in a separate thread (via loop.run_in_executor) and yields each line back to the SSE generator. This way the event loop is never blocked on subprocess I/O.

PYTHONUNBUFFERED=1

Python's stdout is line-buffered when connected to a terminal but block-buffered when connected to a pipe. Subprocesses with stdout piped to the cockpit fall in the second category, so without PYTHONUNBUFFERED=1 the browser would see nothing until the script finishes (or the buffer fills, which for a 4 KB pipe could take several seconds of output). Setting this env var forces line-buffered behavior.

Connection cancellation

If the browser tab closes or the user navigates away, FastAPI's request.is_disconnected() returns true on the next read. The SSE generator catches this and signals the subprocess to terminate, then exits cleanly.

Bake

Bake & Packages — Persistent Snapshots

The Bake feature lets an admin promote the current state of their temp directory into a permanent, shareable package. Once baked, files become visible to all admins on the same project (not just the baker), and they survive the temp directory's 24-hour TTL.

Lifecycle

  1. Admin runs an extraction. Files land in temp/{email}/.
  2. Admin clicks "Bake → Publish package" in the UI.
  3. Cockpit copies all non-_ files from the temp dir into packages/{package_id}/ in blob.
  4. An entry is added to packages_index.json with id, name, files, created_by, created_at, expires_at (default: 30 days).
  5. Other admins on the same project see the package in their packages tab and can preview / download files.
  6. After 30 days, a startup cleanup function (cleanup_expired_packages) removes the index entry and the underlying blobs.

Visibility rules

A package is visible to an admin if the admin is in the project's admins list (per the registry). Cross-project visibility is not allowed even for the package creator — packages are scoped to a project, even if the creator is admin elsewhere too.

Why Forma L1 isn't bakeable

L1 (Account Projects) is global, not per-project. Baking it would create a per-project package that contains data not specific to that project — confusing semantics, and the data goes stale within hours anyway. The bake button is hidden on L1 outputs.

Preview pipeline

For known formats (CSV, small JSON), the cockpit renders an inline preview when the admin clicks a package file. The frontend fetches the file via GET /api/packages/{id}/{file}, parses CSV with PapaParse or pretty-prints JSON, and displays in a modal. Files larger than 10 MB get a "download to view" message instead.

Frontend preview state

The packages tab maintains an in-memory map of { package_id: { previewedFiles: Set, expandedAccordion: bool } } on the client side. This isn't persisted — refreshing the page closes all previews. The state exists only to avoid re-fetching a file the admin has already opened in the same session, since some L3 outputs are large and re-parsing CSV in the browser is noticeable. A WeakMap-style cache could hold the parsed data in memory, but for now the cockpit just re-fetches and re-parses on demand.

Scheduler

Scheduler — Shards & Compilers

The scheduler is a recent addition that lets admins save reusable extraction configurations and (eventually) fire them on a recurring schedule. It introduces two distinct entities — shards and compilers — and is being built in stages. Current state and roadmap below.

The conceptual model

Shard

An atomic, runnable unit. Fully self-contained: script + context + output format + destination. Can be run on demand via "Run now" (planned), or referenced by a compiler. Belongs to at most one compiler at a time. Has its own active/paused state.

Compiler

A schedule wrapper. Holds a frequency / days / time / timezone, plus a list of shard IDs to fire when the schedule hits. Empty compilers are allowed (saved before adding shards). Shards inside a compiler are fired sequentially; failures don't cascade.

What's built today

  • Persistence layer. shards.json, compilers.json, automation_runs.json in cockpit-data. Same load/save/cache pattern as other cockpit JSON files.
  • SCRIPT_CATALOG. A hardcoded dict in app.py listing the 9 schedulable scripts with their platform, display name, and required context fields. Validators reject saves that don't match.
  • CRUD endpoints. Full GET / POST / PUT / DELETE for shards and compilers, plus toggle for active/paused, plus a runs list endpoint, plus the script catalog endpoint. All admin-only via require_user.
  • UI. Three-tab page (Shards / Compilers / Recent runs) with in-place builders, dependent dropdowns wired to the existing /api/projects and /api/forma/models endpoints, and a shard picker modal for adding shards to a compiler.
  • Blob_Client.py. A separate module under codeShared/ for uploading export files to forma-exports / revizto-exports / morta-exports, with a hard guard against accidentally writing to cockpit-data.

What's NOT built yet

  • "Run now." The buttons are visible in the UI but disabled. The runner that fires a shard manually (and uploads its output to blob) is the next building block.
  • Cron firing. Schedules are stored, but nothing fires them yet. APScheduler in-process is the planned engine. Restart-aware via a missed-jobs sweep on startup.
  • Token refresh for headless runs. Manual extractions today rely on the admin being logged in (their tokens are fresh). Scheduled runs have no human; refresh tokens have to be exercised server-side using the shard's created_by stored credentials.
  • Auto-disable. Three consecutive failures should set a shard's auto_disabled flag. The data shape is in place but the firing logic that increments consecutive_failures doesn't exist yet.
  • Egnyte / SharePoint destinations. Greyed out in the UI with "Stage 3" tooltip. Egnyte requires API credentials from ALEC IT; SharePoint requires Azure AD app registration with admin consent.

Shard ↔ compiler link sync

Each shard stores a denormalised in_compiler field (compiler_id or null). After any compiler create/update/delete, _sync_shard_compiler_links() recomputes every shard's in_compiler by scanning the canonical shard_ids arrays in compilers.json and writing back. This keeps the field consistent without forcing the UI to scan all compilers when rendering a shard list.

Why APScheduler instead of Azure Functions Timer

Three reasons. First, the realistic load is modest — handful of automations per day, not thousands — so the missed-jobs risk on App Service restart is acceptable with a startup sweep. Second, in-process scheduling means one deployable unit instead of two; the cockpit doesn't need to coordinate with a separate Azure Functions app. Third, the firing logic lives in the same process as the script subprocess invocation, so there's no IPC overhead and no need to duplicate config-merge logic in a second runtime.

If reliability problems crop up later, swapping to Azure Functions Timer is a single-file change since the firing logic is encapsulated in fire_shard() and fire_compiler().

Frontend

Frontend Event Model

The frontend has no framework — no React, no Vue, no Svelte. Pages are static HTML produced by Jinja2 with progressively-enhanced behavior added by inline scripts and a small amount of shared utility code in static/js/. This is a deliberate choice: zero build pipeline means deploys are git push + az webapp deploy with no Node toolchain involved.

smartFetch

Defined in base.html. A wrapper around fetch() with two-stage rendering: it serves cached data from localStorage immediately for instant paint, then fires the network request and updates the UI on fresh data. Used for routes that benefit from optimistic rendering — projects list, model list, registry data.

smartFetch('/api/projects', 'projects', {
  onCached: (data) => populateDropdowns(data),  // instant paint from localStorage
    onFresh:  (data) => populateDropdowns(data),  // update from network
});

SSE consumption

Live extraction logs are consumed via the browser's EventSource API. The cockpit's stream IDs are short-lived; on tab close, the connection drops and the server-side handler picks this up via request.is_disconnected().

Form patterns

Most forms use vanilla fetch() with JSON bodies, onSubmit handlers, and inline validation. There's no central form library. The toast pattern (#s-toast div, slide-in from bottom) is replicated across pages with small variations.

Deploy

Deploy Pipeline & Operational Discipline

The deploy command

# From the repo root, after committing changes
git push origin main
git archive --format=zip --output=deploy.zip HEAD
az webapp deploy \
  --resource-group digitalcockpit-rg \
  --name digitalcockpit-alec \
  --src-path deploy.zip --type zip

git archive respects .gitignore and only includes committed files. The az webapp deploy call uploads the zip, runs Oryx build (installs requirements.txt), and restarts the worker. Total wall time ~60–90 seconds.

Cross-file dependencies — ship together

Many features touch multiple files at once: a new endpoint in app.py needs a matching frontend handler in a template. Always commit and deploy these together. A partially-deployed feature (server has the new endpoint, frontend doesn't call it) is silent dead code; the inverse (frontend calls a missing endpoint) shows up as 404s in the browser console.

The .gitignore foot-gun

Files that exist locally but are ignored by git won't be in the deploy zip. This is correct for secrets and caches, but occasionally bites when a useful helper script is accidentally .gitignore'd and works locally but goes missing on Azure. After every deploy, sanity-check that the new files actually arrived (see Operational Quirks below).

Credential rotation playbook

  1. Update the platform-side credential (Revizto, Morta, Forma).
  2. For shared Forma: owner updates Settings page, which writes to their config_*.json.
  3. For per-admin Revizto/Morta: each admin updates their own Settings.
  4. For storage connection string: rotate via Storage Account → Access keys → Rotate. Update App Service env var. Worker restarts automatically.
  5. For SESSION_SECRET: regenerate, update env var, accept that all admins need to re-login.

Working with stale local snapshots

The local dev environment has stale state for tokens, registry, and packages. When debugging a production issue locally, beware: the local cockpit-data isn't synced to Azure's. USE_BLOB=false falls back to local ./data/ directory; USE_BLOB=true with the env var pointing at production blob is risky for writes.

Quirks

Operational Quirks & Lessons Learned

The ZIP-deploy file-sync gap

Azure's az webapp deploy --type zip uploads the archive to a staging directory under /tmp/<hash>/, builds it, and is supposed to swap it into /home/site/wwwroot. In practice, when wwwroot contains runtime-generated files (token caches, models cache, leftover state) that aren't part of the zip, the swap step sometimes leaves the new files in /tmp and never copies them across. The deploy command reports Succeeded regardless.

Symptom and fix
If new code doesn't seem to take effect after a deploy, SSH into the App Service and run ls /home/site/wwwroot/. If the new file/folder is missing, find the staging dir under /tmp/<hash>/ and cp -r manually. This is a known Azure issue with no documented workaround at the platform level.

Stale wwwroot files

Files that were once in the repo and have since been removed (or renamed) sometimes persist in wwwroot across deploys. Azure doesn't aggressively prune files that aren't in the new zip. The current production wwwroot still contains a few corrupted leftovers from earlier secret-cleanup commits — harmless but worth tidying when convenient. Manual rm via SSH is the only fix.

The 230-second proxy timeout

Azure's front-end proxy terminates HTTP connections after 230 seconds of inactivity. SSE streams can stay open longer because they emit data periodically — but a single L3 fetch on a Wynn-scale model that goes silent for 4+ minutes will be cut off. The script-side fix is to print a heartbeat line every 30 seconds during long phases.

Memory hardening for Forma L3

Early L3 implementations buffered all element rows in memory before writing the final JSON. This OOM'd on Wynn-scale models (1.4 GB+ of JSON exceeded available RAM). The current implementation streams to per-category temp files and stitches at the end — peak memory stays under 400 MB.

Concurrent write collisions on shared blobs

Two admins saving to projects_registry.json in the same second: last-write-wins, no warning. The cache invalidation pattern means the next read picks up whichever write landed last in blob. There is no optimistic-locking mechanism. For a small admin team this hasn't caused real issues; if it ever does, an ETag check on read+write would solve it.

The .gitignore vs .gitignore foot-gun

A previous commit accidentally renamed .gitignore to gitignore (no leading dot). On Linux this is just a regular file — git doesn't treat it as the ignore manifest. Caught and fixed; the corrupted file still lingers in production wwwroot.

Growth rates worth watching

  • invite_log.json — append-only, no trim. Currently kilobytes; will grow to MBs over years. Worth adding a yearly archive pattern eventually.
  • automation_runs.json — capped at 1,000 entries via in-place trim on every write. Won't grow unbounded.
  • cockpit-data/packages/ — auto-cleaned on app startup if expires_at < now.
  • forma-/revizto-/morta-exports — capped by the 15-day lifecycle rule. Worst case is 15 × max-daily-output, well below storage account quotas.

What scaling up looks like

If load grows beyond what B1 handles, the upgrade path is:

  1. B2 / B3 — same shape, more RAM (3.5 / 7 GB). Drop-in upgrade. ~$50/mo step.
  2. Premium V3 P0/P1 — actual hot-restart isolation, deployment slots for blue-green. Justified when downtime starts mattering.
  3. Multi-instance — needs concurrency safety on the cache invalidation and the scheduler. Not free; postpone until single-instance is genuinely the bottleneck.

Roadmap

Roadmap & Known Deferred Work

Items below are explicitly known and intentionally deferred. Listed here so future maintainers (or Claude) can see the full picture rather than re-deriving it from issue trackers.

Scheduler — Run now

Manual fire endpoint for shards and compilers. Token refresh helpers for headless runs. Output upload via Blob_Client.py. Run records appended to automation_runs.json. Auto-disable counter logic. Next building block.

Scheduler — Cron firing

APScheduler in-process. Missed-jobs sweep on startup. fire_compiler() dispatches to fire_shard() sequentially. Wired into FastAPI startup hook.

SharePoint destination

Azure AD app registration with Microsoft Graph permissions. Admin consent from ALEC IT. App-only auth via MSAL. Stage 3 blocker: ALEC IT availability.

Egnyte API destination

Egnyte API key from ALEC IT. Service account or admin-token model. Same staging as SharePoint.

Morta upsert / append / replace

Push extraction outputs back into Morta tables. Three modes: append rows, replace all rows, upsert by key column. Adds a fourth destination type to the scheduler.

Email notifications on failure

When a scheduled run fails, ACS email the shard's created_by with the error. Optional per-shard recipient override. Deferred until "Run now" + cron are both shipping.

Take-ownership for orphaned shards

If a shard's created_by admin leaves ALEC, their tokens get revoked and all their shards stop firing. A take-ownership button on the shard would re-point created_by to the current admin (after they confirm they have the right credentials).

Password hashing upgrade

SHA-256 → Argon2id with per-user salt. Migration via login-time rehash. Low priority while the cockpit stays internal.

Multi-instance safety

If App Service scales to 2 workers, both will fire scheduled jobs and invalidate each other's caches. Optimistic locking via blob ETag, plus job claiming via automation_runs.json. Postponed until needed.

Forma custom report builder

Admin-configurable Revit-style schedules — pick a category, pick fields to include, save as a report definition. Generates a custom L4-equivalent on demand. Long-term roadmap.
